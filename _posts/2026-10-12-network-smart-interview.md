## 四、面试回答通用模板

网络问题建议按这个结构回答：

1. 先给结论。
2. 放到分层模型里说明它在哪一层。
3. 讲关键流程。
4. 讲为什么这样设计。
5. 补充工程场景和常见问题。

示例：

> TCP 是传输层协议，提供面向连接、可靠、有序、字节流传输。它通过序列号、确认应答、超时重传、流量控制和拥塞控制保证可靠性。相比 UDP，TCP 成本更高，但适合文件传输、HTTP 等要求可靠性的场景。

## 五、P0 高频问题清单

### 1. 网络模型

必须会答：

- OSI 七层和 TCP/IP 四层分别是什么？
- 每一层负责什么？
- TCP、IP、HTTP、DNS、ARP 分别在哪一层？
- 数据从应用发送到网卡经过哪些封装？

面试表达重点：

> TCP/IP 更贴近实际工程。应用层负责应用协议，如 HTTP、DNS；传输层负责端到端传输，如 TCP/UDP；网络层负责 IP 寻址和路由；网络接口层负责局域网内传输和 MAC 寻址。发送数据时会逐层封装，接收时逐层解封装。

### 2. 输入 URL 到页面展示

必须会答：

- 输入 URL 后发生了什么？
- DNS 查询过程是什么？
- TCP 和 TLS 在哪里发生？
- HTTP 请求和响应之后浏览器如何渲染？

面试表达重点：

> 流程可以概括为：解析 URL、检查缓存、DNS 解析得到 IP、建立 TCP 连接、HTTPS 场景进行 TLS 握手、发送 HTTP 请求、服务器处理并返回响应、浏览器解析 HTML/CSS/JS 并渲染页面，最后根据连接策略复用或关闭连接。

### 3. HTTP 报文、方法和状态码

必须会答：

- HTTP 请求报文和响应报文结构？
- GET 和 POST 区别？
- 常见状态码有哪些？
- 301 和 302 区别？401 和 403 区别？502 和 504 区别？

面试表达重点：

> HTTP 请求由请求行、请求头、空行、请求体组成；响应由状态行、响应头、空行、响应体组成。GET 通常用于获取资源，参数常放 URL，具备幂等语义；POST 通常用于提交数据，请求体承载数据，一般不要求幂等。

常见状态码速记：

| 状态码 | 含义 |
|---|---|
| 200 | 成功 |
| 301 | 永久重定向 |
| 302 | 临时重定向 |
| 304 | 协商缓存命中 |
| 400 | 请求错误 |
| 401 | 未认证 |
| 403 | 无权限 |
| 404 | 资源不存在 |
| 500 | 服务端错误 |
| 502 | 网关收到上游错误响应 |
| 504 | 网关等待上游超时 |

### 4. HTTP 版本

必须会答：

- HTTP/1.0 和 HTTP/1.1 区别？
- HTTP/1.1 和 HTTP/2 区别？
- HTTP/3 为什么基于 QUIC？

面试表达重点：

> HTTP/1.1 相比 1.0 引入长连接、管线化和更完善的缓存控制。HTTP/2 使用二进制分帧、多路复用、头部压缩，缓解队头阻塞。HTTP/3 基于 QUIC 和 UDP，把连接管理、可靠传输、拥塞控制放到用户态，减少 TCP 层队头阻塞并优化握手时延。

### 5. HTTP 缓存

必须会答：

- 强缓存和协商缓存区别？
- Cache-Control、Expires、ETag、Last-Modified 分别是什么？
- 304 是什么意思？

面试表达重点：

> 强缓存命中时不需要请求服务器，常由 Cache-Control 或 Expires 控制；协商缓存需要向服务器验证资源是否变化，常用 ETag/If-None-Match 或 Last-Modified/If-Modified-Since。服务器返回 304 表示资源未变化，客户端继续使用本地缓存。

### 6. Cookie 和 Session

必须会答：

- Cookie 和 Session 区别？
- Cookie 工作原理？
- Session 如何识别用户？
- Token 和 Session 有什么不同？

面试表达重点：

> Cookie 存在客户端，每次请求可自动携带；Session 存在服务端，客户端通常通过 Cookie 中的 session id 关联服务端状态。Cookie 适合保存少量非敏感标识，Session 适合保存服务端会话状态。

### 7. HTTPS 和 TLS

必须会答：

- HTTP 和 HTTPS 区别？
- HTTPS 如何保证安全？
- TLS 握手过程是什么？
- 为什么既用非对称加密又用对称加密？
- 证书解决什么问题？

面试表达重点：

> HTTPS = HTTP + TLS。TLS 主要提供身份认证、数据加密和完整性保护。非对称加密用于身份认证和安全协商密钥，对称加密用于后续大量数据传输，因为效率更高。证书用于证明服务端公钥的可信性，避免中间人伪造。

### 8. TCP 和 UDP

必须会答：

- TCP 和 UDP 区别？
- TCP 如何保证可靠传输？
- UDP 适合什么场景？
- 如何基于 UDP 实现可靠传输？

面试表达重点：

> TCP 面向连接、可靠、有序、字节流，有流量控制和拥塞控制；UDP 无连接、不保证可靠和有序，但开销小、时延低，适合音视频、游戏、DNS 等场景。如果要可靠 UDP，需要在应用层实现序列号、ACK、重传、去重、排序和拥塞控制。

### 9. 三次握手

必须会答：

- 三次握手过程？
- 为什么不是两次？
- SYN 洪泛是什么？
- 初始序列号有什么作用？

面试表达重点：

> 三次握手的核心是双方确认彼此的发送和接收能力，并同步初始序列号。两次握手无法让客户端确认服务端的发送能力，也容易让历史连接请求导致服务端建立无效连接。

### 10. 四次挥手和 TIME_WAIT

必须会答：

- 四次挥手过程？
- 为什么挥手通常需要四次？
- TIME_WAIT 为什么存在？
- TIME_WAIT 过多怎么办？

面试表达重点：

> TCP 是全双工连接，关闭时双方发送方向需要分别关闭，所以通常需要四次挥手。TIME_WAIT 的作用是确保最后一个 ACK 能被对方收到，并让旧连接中的迟到报文在网络中消失，避免影响新连接。

### 11. 流量控制和拥塞控制

必须会答：

- 流量控制解决什么问题？
- 拥塞控制解决什么问题？
- 滑动窗口是什么？
- 慢启动、拥塞避免、快重传、快恢复是什么？

面试表达重点：

> 流量控制关注接收方是否来得及接收，通过接收窗口限制发送速度；拥塞控制关注网络是否承载得住，通过拥塞窗口动态调整发送速率。TCP 实际发送窗口通常取接收窗口和拥塞窗口的较小值。

### 12. 粘包和拆包

必须会答：

- TCP 为什么会粘包？
- UDP 会不会粘包？
- 如何解决粘包和拆包？

面试表达重点：

> TCP 是面向字节流的协议，没有消息边界，应用层多次写入的数据可能被合并发送，一次写入的数据也可能被拆分接收。解决方法是在应用层设计协议边界，比如固定长度、分隔符、长度字段、TLV 格式等。

## 九、按优先级整理的面试答案库

这一节按 P0、P1、P2 排列。每个问题都补充“协议解决什么问题、底层如何工作、什么时候使用、边界和故障信号”。网络题不要只背协议名，排障时要能把一次请求拆成可观测的阶段。

## P0：必须优先掌握

### 1. OSI 七层和 TCP/IP 四层分别是什么？

OSI 是便于教学和分析的七层模型：应用、表示、会话、传输、网络、数据链路、物理。TCP/IP 更贴近工程，通常合并为应用层、传输层、网络层、网络接口层。模型不是说每个协议只能属于一层，而是帮助划分职责和故障边界。

| TCP/IP 层 | 主要职责 | 常见协议或对象 |
|---|---|---|
| 应用层 | 定义业务消息、状态和错误语义 | HTTP、DNS、TLS、SMTP |
| 传输层 | 端到端传输、端口、可靠性或低延迟 | TCP、UDP、QUIC |
| 网络层 | IP 寻址、路由和分片/转发 | IPv4/IPv6、ICMP |
| 网络接口层 | 在链路上传输帧，处理 MAC 和介质访问 | Ethernet、Wi-Fi、ARP |

**具体使用：** 访问失败时先确认 DNS/HTTP 层是否有错误，再看 TCP 连接和重传，最后看路由、ARP、网卡和链路。分层的价值是缩小范围，不是强行按模型顺序猜原因。

**边界：** TLS 常被放在应用层和传输层之间；ARP 也常被称为网络层与链路层之间的协议。面试时说明“按教材划分可能略有不同，但职责明确”即可。

### 2. TCP、IP、HTTP、DNS、ARP 分别解决什么问题？

HTTP 定义应用请求和响应；DNS 把域名映射到地址或其他记录；TCP 提供有序可靠字节流；IP 负责跨网络寻址和路由；ARP 在 IPv4 局域网中把下一跳 IP 解析为 MAC。

一次 HTTP 请求通常是“HTTP 消息 -> TCP 字节流 -> IP 数据包 -> 链路帧”。每层增加自己的头部，接收端反向解析。发送给非本地网段时，ARP 查询的是默认网关的 MAC，而不是远端服务器的 MAC。

**排查边界：** DNS 正常不代表 TCP 端口开放；能建立 TCP 不代表 HTTP 路由、证书或业务处理正确；ARP 正常也不代表跨网段路由可达。使用 `dig/nslookup`、`ss`、`curl -v`、抓包分层验证。

### 3. 输入 URL 到页面展示发生了什么？

可以按阶段回答：URL 解析与缓存 -> DNS -> 代理/路由选择 -> TCP 或 QUIC 建连 -> TLS 握手 -> HTTP 请求 -> 服务端处理 -> 响应下载 -> HTML/CSS/JS 解析 -> 布局、绘制和合成。

**具体机制：** 浏览器可能先命中强缓存而不发请求；DNS 结果可能来自浏览器、系统、本地递归 DNS 或 DoH；HTTPS 还需验证证书和协商密钥；HTTP/2 或 HTTP/3 可以复用一条连接承载多个资源。页面“可见”不等于所有资源下载完成，首字节、首屏和完全加载是不同指标。

**排查方法：** 用浏览器 Network 面板拆分 DNS、连接、TLS、TTFB、下载和渲染时间；服务端用 request id 关联网关、应用和数据库日志。页面慢可能是后端慢，也可能是资源太大、缓存失效、主线程执行 JS 或布局抖动，不能统称为“网络问题”。

### 4. DNS 查询过程是什么？

客户端通常先查浏览器缓存、操作系统缓存和 hosts，再向配置的递归 DNS 查询。递归服务器没有缓存时，会依次查询根、顶级域和权威 DNS，得到 A/AAAA、CNAME 等记录后按 TTL 缓存并返回。

**核心机制：** DNS 是分布式、缓存驱动的层级系统；TTL 越长，查询压力和延迟通常越低，但变更传播越慢。CNAME 会引入额外查询，A/AAAA 可能返回多个地址用于容灾或负载调度。DNS 查询本身可以走 UDP，也可能因响应过大、策略或加密 DNS 使用 TCP/HTTPS/TLS。

**常见问题：** 解析到错误地址可能是缓存、地域调度或 DNS 劫持；解析成功但连接失败可能是 IPv6 优先、端口、防火墙或路由问题。排查时比较不同递归 DNS、记录 TTL、A/AAAA 结果和实际连接时间，不能只执行一次 `ping`。

### 5. HTTP 请求报文和响应报文结构是什么？

HTTP/1.x 报文由起始行、头部、空行和可选消息体组成：请求行包含方法、目标和版本；响应状态行包含版本、状态码和原因短语。头部表达 Host、内容类型、长度、缓存、认证、Cookie 等元数据。

**具体使用：** `Content-Length` 或分块编码决定消息体边界；`Content-Type` 描述如何解释内容；`Accept` 描述客户端能接受什么；缓存、压缩和鉴权通常通过头部协商。HTTP/2/3 会二进制分帧，但应用语义仍然是方法、头部和内容。

**常见问题：** 请求体存在不代表服务端一定读取；代理可能重写头部；错误的 `Content-Length` 会造成截断或请求串联风险；日志中记录 Authorization、Cookie 和 URL 查询参数可能泄露敏感信息。

### 6. GET 和 POST 有什么区别？

核心区别是语义：GET 用于获取资源，通常应安全且幂等；POST 用于提交数据、创建资源或触发动作，通常可能改变服务端状态。参数位置不是本质区别，GET 也可以有请求体，但实际兼容性和缓存行为较差。

**具体使用：** 查询接口优先用 GET，并让相同 URL 可重复请求；创建订单、上传文件和提交表单通常用 POST。POST 并不自动防重复，支付、下单等接口应通过幂等键、业务唯一号或去重表处理重试。

**安全边界：** HTTPS 下两者传输都可加密，但 GET 参数更容易出现在历史记录、代理和访问日志中；POST 也可能被日志记录。不要把“用 POST”当作权限控制，认证、授权、CSRF 防护和输入校验仍需独立实现。

### 7. 常见 HTTP 状态码有哪些？

| 范围/状态 | 含义和使用 |
|---|---|
| 200 | 请求成功并返回表示结果 |
| 201/202/204 | 已创建、已接受异步处理、成功但无内容 |
| 301/302/307/308 | 重定向；307/308 更明确保留原方法和请求体 |
| 304 | 协商缓存命中，响应通常无资源体 |
| 400/422 | 请求格式或业务参数校验失败 |
| 401/403 | 未认证/已认证但无权限 |
| 404/405 | 资源不存在/方法不允许 |
| 409/429 | 状态冲突/限流 |
| 500/502/503/504 | 服务内部错误、网关上游错误、暂不可用、上游超时 |

**排障重点：** 状态码只描述 HTTP 层结果，不能单独说明根因。502 要看网关与上游连接，504 要区分上游处理慢、连接池耗尽和网络丢包；429 要看限流维度和 `Retry-After`。不要把所有业务失败都返回 200，否则监控、重试和客户端处理都会失真。

### 8. HTTP/1.0、HTTP/1.1、HTTP/2、HTTP/3 有什么区别？

| 版本 | 核心机制 | 边界和问题 |
|---|---|---|
| HTTP/1.0 | 通常短连接，每次请求可能重新建连 | 建连开销大，连接复用弱 |
| HTTP/1.1 | 默认持久连接、Host、分块传输和更完整缓存 | 同一连接上的请求仍可能受队头阻塞影响 |
| HTTP/2 | 二进制分帧、单连接多路复用、HPACK 头压缩 | TCP 丢包仍会阻塞该连接上的所有流；服务端推送已较少使用 |
| HTTP/3 | HTTP 运行在 QUIC 上，QUIC 基于 UDP | 需要新的部署、监控和防火墙兼容性 |

HTTP/2 的多路复用解决了 HTTP 层多个请求争抢连接的问题，但没有消除 TCP 层队头阻塞；HTTP/3 把可靠传输拆成独立流，单个流丢包通常不阻塞其他流。

### 9. HTTP 和 HTTPS 有什么区别？

HTTPS 是 HTTP over TLS，提供机密性、完整性和服务器身份认证。HTTP 本身不负责加密，容易被窃听、篡改或伪造；HTTPS 默认使用 443 只是约定，真正的安全性来自 TLS 配置和证书验证。

**具体使用：** 通过证书链验证域名身份，通过会话密钥加密业务数据，通过认证标签检测篡改。生产环境应启用现代 TLS、正确配置证书链、关闭过时协议和弱算法，并考虑 HSTS。

**不足：** TLS 会增加握手、CPU 和证书运维成本；证书过期、域名不匹配、代理中间人配置错误都会导致失败。HTTPS 不能防止应用自身的越权、SQL 注入、恶意脚本或服务端日志泄露，也不能隐藏所有流量特征。

### 10. HTTPS 为什么既用非对称加密又用对称加密？

非对称密码用于身份认证和密钥协商，解决“没有共享密钥如何安全建立会话”的问题；对称密码用于后续大量数据传输，解决吞吐和延迟问题。非对称运算昂贵，不适合直接加密整个响应体。

现代 TLS 通常使用临时密钥交换获得前向保密，证书中的服务器私钥用于签名认证，而不是简单地把全部业务数据用公钥加密。握手完成后双方使用会话密钥进行对称加密和完整性校验。

### 11. TLS 握手大致过程是什么？

简化流程是：客户端发送支持的版本、随机数和密码套件；服务端选择参数、返回证书和密钥交换材料；客户端验证证书链、域名和有效期；双方通过密钥交换计算相同的会话密钥；双方用 Finished 消息确认握手 transcript 未被篡改，之后加密传输应用数据。

**具体排查：** TLS 慢可能来自证书链下载、算法协商、CPU、会话恢复未命中或网络 RTT；TLS 失败可能来自时间错误、SNI、证书链不完整、信任根缺失和协议版本不兼容。用 `curl -v`、openssl s_client、浏览器安全面板和抓包区分 TCP 成功但 TLS 失败的情况。

### 12. 强缓存和协商缓存有什么区别？

强缓存命中时客户端直接使用本地资源，通常不发起验证请求；协商缓存仍发请求，但只传元信息，由服务端判断资源是否变化，未变化返回 304。

| 类型 | 常见头 | 解决的问题 |
|---|---|---|
| 强缓存 | `Cache-Control: max-age`、`Expires` | 减少请求次数和延迟 |
| 协商缓存 | `ETag`/`If-None-Match`、`Last-Modified`/`If-Modified-Since` | 减少响应体传输 |

**具体使用：** 带内容哈希的静态文件可以设置较长 max-age；HTML 入口和动态 API 通常使用较短缓存或协商缓存。发布系统必须保证资源版本、缓存键和回滚策略一致，否则长缓存可能让用户拿到旧代码。

**常见问题：** `no-cache` 通常表示需要重新验证，不是“不允许缓存”；`no-store` 才是不存储。ETag 生成不稳定、代理改写头部、Vary 配置遗漏都会造成缓存失效或错误复用。

### 13. Cookie 和 Session 有什么区别？

Cookie 是浏览器保存并按域、路径和属性自动发送的小型客户端数据；Session 是服务端维护的会话状态，浏览器通常只保存一个 session id。Session 不天然更安全，安全性取决于 id 的随机性、传输保护和 Cookie 属性。

**具体使用：** 登录状态可使用 `Secure`、`HttpOnly`、合适的 `SameSite` 和过期时间；分布式服务可把 session 放入共享存储，或改用无状态 token。Cookie 大小和数量有限，不适合保存大对象或敏感明文。

**边界：** Session 需要处理过期、注销、并发登录和存储故障；token 便于水平扩展，但撤销和密钥轮换更复杂。Cookie 自动携带会带来 CSRF 风险，不能仅靠 CORS 解决，应结合 SameSite、CSRF token 和服务端校验。

### 14. TCP 和 UDP 有什么区别？

| 对比项 | TCP | UDP |
|---|---|---|
| 数据语义 | 有序可靠字节流 | 独立数据报，可能丢失、重复、乱序 |
| 建连 | 有连接状态 | 无握手连接 |
| 控制 | 重传、流量控制、拥塞控制 | 由应用自己决定 |
| 适用 | 文件、HTTP、数据库等可靠传输 | DNS、实时音视频、游戏、QUIC |

TCP 不保证“低延迟”，UDP 也不保证“更快”；UDP 省掉了内置可靠性，但应用若补齐重传、排序和拥塞控制，复杂度可能接近 TCP。选择依据应是消息边界、可靠性、延迟、广播/多播和部署环境，而不是协议名。

### 15. TCP 如何保证可靠传输？

TCP 用序列号标记字节范围，ACK 确认已收到的数据，校验和发现损坏，超时或重复 ACK 触发重传，滑动窗口允许多个报文在途。接收窗口 `rwnd` 保护接收方，拥塞窗口 `cwnd` 估计网络承载能力，实际发送窗口通常取两者较小值。

**常见问题：** TCP 可靠只保证连接内字节最终按序交付，不保证业务请求一定成功；连接断开、服务处理失败和应用超时仍需业务层处理。重传会提高可靠性，但会增加延迟，不能靠无限重传解决网络故障。

### 16. 三次握手过程是什么？为什么不是两次？

客户端发送 SYN 并携带初始序列号，服务端回复 SYN+ACK，客户端再发送 ACK。三次交互让双方确认发送和接收方向都可用，并同步各自的初始序列号。

**具体机制：** 服务端收到第一个 SYN 后会分配半连接状态；最后一个 ACK 到达后才建立完整连接。两次握手无法让服务端确认客户端收到自己的响应，也更容易把延迟到达的旧 SYN 误当成新连接。高并发 SYN 洪泛时，半连接队列和 SYN cookies 是重要防护点。

### 17. 四次挥手过程是什么？为什么通常需要四次？

主动关闭方发送 FIN，表示自己不再发送；对端先 ACK，但仍可能继续发送剩余数据；数据发送完后再发送 FIN；主动方最后 ACK 并进入 TIME_WAIT。两个方向独立关闭，所以通常是四步，ACK 和 FIN 也可能因数据发送完毕而合并。

**常见问题：** `close` 后仍可能有缓冲数据在发送；半关闭连接要用 `shutdown` 等语义明确的操作。异常断开、RST 和进程崩溃不会严格遵循四次挥手，排查时应结合抓包和 socket 状态。

### 18. TIME_WAIT 为什么存在？

主动关闭方进入 TIME_WAIT，主要为了：最后 ACK 丢失时可以响应对方重发的 FIN；等待旧连接中的延迟报文消失，避免相同四元组的新连接被旧报文干扰。它不是“连接还在使用”，但会占用内核连接状态和本地端口资源。

**具体排查：** 大量 TIME_WAIT 通常说明本端主动关闭很多短连接，优先检查连接池、Keep-Alive、重试和上游异常。不要直接关闭 TIME_WAIT 或盲目调整内核参数，错误设置可能导致旧报文污染新连接或掩盖业务问题。

## P1：传输层进阶和工程常问

### 19. 流量控制和拥塞控制有什么区别？

流量控制保护接收方，接收方通过通告窗口告诉发送方自己还能接收多少；拥塞控制保护网络，发送方根据丢包、RTT 和 ACK 行为估计链路负载。两者独立但共同限制发送速率，`send_window = min(rwnd, cwnd)` 是常见概念表达。

**排查方法：** 接收窗口很小要看应用是否及时读取；拥塞窗口受限要看丢包、RTT 和重传。服务端 CPU 低但吞吐低，可能是接收端消费慢、网络拥塞或窗口配置问题，不能只看带宽。

### 20. 拥塞控制有哪些阶段？

典型教材模型包含慢启动、拥塞避免、快速重传和快速恢复：连接开始时窗口快速增长；达到阈值后转为较慢增长；重复 ACK 暗示报文可能丢失时提前重传；发生拥塞后降低发送窗口。

现代算法可能使用 BBR 等不同信号，不应把“指数增长/线性增长”当成所有系统的精确实现。拥塞控制的目标是提高吞吐，同时控制丢包和排队延迟；高带宽长距离链路需要结合 RTT、缓冲区和算法特性评估。

### 21. TCP 粘包和拆包是什么？如何解决？

TCP 只提供有序字节流，不保存应用层消息边界。多次 `send` 可能一次 `recv` 读出，叫粘包；一次 `send` 也可能多次 `recv` 才读完，叫拆包。这不是 TCP 错误，而是应用没有定义消息边界。

常见协议设计：固定长度、分隔符、长度前缀、TLV 或自描述格式。解析器必须处理半包、多个完整包、非法长度、超大消息和连接中途关闭；长度字段要限制上限，避免恶意输入触发内存分配。

### 22. HTTP Keep-Alive 和 TCP Keepalive 有什么区别？

HTTP Keep-Alive 是应用层连接复用，让多个 HTTP 请求共享一个 TCP/TLS 连接，减少握手和端口消耗。TCP keepalive 是内核定时发送探测包，检测长时间空闲连接是否仍可达。

**适用边界：** HTTP 连接复用需要连接池、空闲超时和最大请求数策略；TCP keepalive 间隔通常较长，不能替代业务级请求超时和健康检查。长连接如果没有上限，可能占满 fd、内存和连接池，仍需限制并发和空闲连接。

### 23. 如何实现可靠 UDP？

应用层至少要设计序列号、确认、超时重传、重复检测、乱序重排、窗口、流量/拥塞控制和连接关闭语义。实时音视频有时宁可丢弃过期帧，也不等待重传；文件传输则更重视完整性和顺序。

**核心取舍：** 可靠 UDP 不是“把 TCP 重新写一遍”，而是只实现业务真正需要的可靠性。自己实现容易遗漏 RTO、拥塞公平性、攻击防护和 NAT 行为；如果没有明确需求，应直接使用 TCP 或成熟的 QUIC/可靠传输库。

### 24. TIME_WAIT 过多怎么办？

先用 `ss -ant state time-wait`、连接日志和抓包确认哪一方主动关闭，再检查短连接、连接池失效、请求超时重试、服务重启和上游异常。优化通常包括连接复用、合理的空闲超时、批量请求和减少无意义重连。

系统参数只能作为容量治理的一部分，不能替代业务修复。还要区分 TIME_WAIT 数量和真正的端口耗尽、fd 耗尽、内存压力；三者解决方式不同。

## P2：补充广度和新协议

### 25. CDN 是什么？有什么作用？

CDN 在靠近用户的边缘节点缓存或代理内容，用户通过 DNS、HTTP 调度或 Anycast 被导向合适节点。命中缓存时无需访问源站，可降低延迟、源站带宽和突发流量压力。

**具体使用：** 带版本号的静态 JS/CSS/图片适合长缓存；动态接口通常需要鉴权、缓存键和回源策略。要关注命中率、回源率、节点延迟、缓存失效、区域差异和源站保护。

**常见问题：** 缓存键缺少 Host、查询参数或鉴权维度会导致错误内容泄露；刷新缓存可能有传播延迟；CDN 命中不代表首屏一定快，浏览器解析和主线程仍可能是瓶颈。

### 26. NAT 解决什么问题？

NAT 将内网私有地址和端口映射为公网地址和端口，使多个内网设备共享 IPv4 公网地址，也隐藏了内部地址结构。出站连接通常容易建立，入站连接需要端口映射、UPnP 或 NAT 穿透。

**边界：** NAT 不是完整防火墙，也不是安全边界的替代品；它破坏端到端可达性，可能影响 P2P、VoIP、游戏和主动回连。排查连接问题时要区分对称 NAT、端口映射过期、双重 NAT 和防火墙策略。

### 27. `ping` 的原理是什么？

`ping` 发送 ICMP Echo Request，目标返回 Echo Reply，通过 RTT、丢包和 TTL 等信息观察网络层可达性。它只验证某种 ICMP 路径，不验证 TCP 端口、TLS、HTTP 路由或业务健康。

**常见误区：** ping 不通可能是防火墙限 ICMP，ping 通也可能存在 TCP 被拒绝、应用超时或负载过高。应结合 `traceroute`/`tracert`、`ss`、`curl` 和抓包，区分路径、端口和应用层问题。

### 28. HTTP/3 和 QUIC 有什么特点？

QUIC 基于 UDP，但在用户态实现连接标识、可靠传输、拥塞控制、TLS 1.3 和多路复用；HTTP/3 定义了在 QUIC 流上的 HTTP 语义。不同请求使用独立流，一个流丢包通常不会阻塞其他流，并支持网络切换时保持连接标识。

**不足：** 需要服务端、客户端、负载均衡、监控和防火墙共同支持；UDP 可能被网络设备限速或阻断，调试工具和指标体系也需更新。HTTP/3 并不保证任何网络都更快，应比较握手、丢包、CPU 和真实用户体验。

### 29. 访问一个网站很慢，如何排查？

按阶段建立时间线：DNS、代理选择、TCP/QUIC 建连、TLS、请求排队、服务端处理、响应下载、浏览器解析和渲染。每一阶段都要有数据，而不是只看总耗时。

**具体工具：** 浏览器 Network 看 waterfall 和缓存；`curl -w` 拆分 DNS/连接/TLS/首字节；`dig` 查解析；`ss` 看连接状态；抓包看重传、窗口和握手；服务端 trace 看网关、应用、数据库和下游调用。慢请求要关联 request id，区分偶发尖峰和持续容量不足。

**常见结论：** DNS 慢不等于服务慢，TTFB 高不等于下载慢，下载慢不一定是带宽不足，页面白屏也可能是 JS 阻塞。排查结束应给出可验证的瓶颈和修复前后指标。

### 30. 常见端口号有哪些？

| 端口 | 常见协议/服务 |
|---|---|
| 20/21 | FTP 数据/控制 |
| 22 | SSH |
| 25/587 | SMTP/邮件提交 |
| 53 | DNS |
| 80/443 | HTTP/HTTPS |
| 110/143 | POP3/IMAP |
| 3306 | MySQL |
| 5432 | PostgreSQL |
| 6379 | Redis |
| 8080/8443 | 常见的 HTTP/HTTPS 备用端口 |

端口号只是约定，不能据此断言服务类型；服务可以监听任意端口，容器、反向代理和 NAT 还可能改变外部端口。排查时用 `ss -lntup`、`lsof -i`、服务配置和实际握手确认，而不是只看端口表。
