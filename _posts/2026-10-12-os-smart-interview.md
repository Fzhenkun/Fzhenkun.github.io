## 四、面试回答通用模板

操作系统问题建议用这个结构：

1. 先定义概念。
2. 再说明系统为什么需要它。
3. 然后讲底层机制或关键流程。
4. 最后结合程序问题：崩溃、卡顿、内存、CPU、IO。

示例：

> 虚拟内存是操作系统为进程提供的抽象地址空间。它让每个进程看起来都拥有连续独立的内存空间，实际通过页表映射到物理内存。这样可以实现进程隔离、内存保护、按需加载和更大的地址空间。实际排查内存问题时，要区分虚拟地址空间占用、物理内存占用和提交内存。

## 五、P0 高频问题清单

### 1. 进程和线程

必须会答：

- 进程和线程的区别？
- 为什么线程切换比进程切换开销小？
- 同一进程内线程共享什么，独占什么？
- 协程和线程有什么区别？

面试表达重点：

> 进程是资源分配的基本单位，线程是 CPU 调度的基本单位。同一进程内多个线程共享地址空间、全局变量、堆、文件句柄等资源，但每个线程有自己的栈、寄存器上下文和程序计数器。因此线程通信方便，但一个线程出错可能影响整个进程。

### 2. 用户态和内核态

必须会答：

- 为什么要区分用户态和内核态？
- 什么情况下会从用户态切到内核态？
- 系统调用、中断、异常有什么关系？
- 用户态/内核态切换为什么有开销？

面试表达重点：

> 用户态限制普通程序直接访问硬件和关键内存，内核态拥有更高权限。程序访问文件、网络、进程管理等资源时，需要通过系统调用进入内核态。切换涉及上下文保存、权限切换和内核路径执行，因此频繁系统调用会带来性能开销。

### 3. 并发、并行和上下文切换

必须会答：

- 并发和并行区别？
- 什么是上下文切换？
- 上下文切换为什么影响性能？
- 线程是不是越多越好？

面试表达重点：

> 并发是同一时间段处理多个任务，并行是同一时刻多个任务真正同时运行。线程过多会增加调度和上下文切换成本，还可能带来锁竞争、缓存失效、内存占用增加，所以线程数要结合 CPU 核数、任务类型和阻塞比例设计。

### 4. 同步、互斥和死锁

必须会答：

- 同步和互斥区别？
- mutex、semaphore、condition_variable 分别解决什么问题？
- 死锁四个必要条件是什么？
- 如何避免死锁？

面试表达重点：

> 互斥解决同一时间只有一个线程访问共享资源的问题，同步解决多个线程按某种顺序协作的问题。死锁通常由互斥、持有并等待、不可抢占、循环等待四个条件共同导致。工程上可以通过固定加锁顺序、减少锁嵌套、及时释放锁、使用超时锁和 RAII 锁降低风险。

### 5. 虚拟内存

必须会答：

- 什么是虚拟内存？
- 虚拟地址如何映射到物理地址？
- 页表和 TLB 的作用是什么？
- 缺页中断是什么？
- 虚拟内存有什么好处？

面试表达重点：

> 虚拟内存通过页表把进程虚拟地址映射到物理内存。TLB 是页表缓存，用来加速地址转换。访问的页不在物理内存时会触发缺页中断，由操作系统加载页面。虚拟内存带来进程隔离、内存保护、按需加载和更灵活的内存管理。

### 6. 堆和栈

必须会答：

- 堆和栈区别？
- 栈溢出原因有哪些？
- 堆内存泄漏如何产生？
- 为什么递归过深可能崩溃？

面试表达重点：

> 栈由系统自动管理，主要存放函数调用帧、局部变量、返回地址等，空间通常较小；堆由程序动态申请释放，空间更大但需要管理生命周期。递归过深、大对象放栈上、局部数组过大都可能导致栈溢出。

### 7. 页面置换和内存碎片

必须会答：

- 页面置换算法有哪些？
- 什么是局部性原理？
- 内部碎片和外部碎片区别？
- 为什么频繁缺页会导致性能下降？

面试表达重点：

> 局部性原理包括时间局部性和空间局部性，是缓存、分页、预取等机制的基础。缺页会触发磁盘或后备存储访问，成本远高于内存访问，频繁缺页会造成系统抖动，表现为响应慢、CPU 等待增加。

### 8. IPC 进程间通信

必须会答：

- 进程间通信方式有哪些？
- 管道、消息队列、共享内存、socket 各自适合什么场景？
- 共享内存为什么快？
- 共享内存为什么还需要同步机制？

面试表达重点：

> 共享内存快是因为多个进程把同一块物理内存映射到各自地址空间，避免了频繁内核拷贝。但共享内存只解决数据共享，不解决并发访问顺序，因此通常需要信号量、互斥锁等同步机制配合。

### 9. select、poll、epoll

必须会答：

- select、poll、epoll 的区别？
- epoll 为什么适合高并发？
- 水平触发和边缘触发区别？
- epoll 一定比 select 快吗？

面试表达重点：

> select 和 poll 每次调用都需要传入关注的 fd 集合，并扫描查找就绪事件；epoll 通过内核维护事件集合，就绪事件通过回调加入就绪队列，应用只取就绪列表，因此在大量连接但活跃连接较少时更高效。

### 10. 系统问题定位

必须会答：

- CPU 负载过高如何定位？
- 进程内存持续上涨如何定位？
- 程序卡顿如何定位？
- 死锁如何定位？

面试表达重点：

> 我会先确认现象和范围，再采集数据。CPU 高看进程和线程热点，结合 top、perf、采样或性能工具；内存高看虚拟内存、物理内存、对象增长和泄漏路径；卡顿看主线程、锁等待、IO 阻塞和调度；死锁看线程调用栈和锁持有关系。

## 七、面试前 30 分钟速记

- 进程是资源分配单位，线程是调度单位。
- 用户态通过系统调用进入内核态。
- 线程不是越多越好，过多会导致切换和竞争。
- 同步管顺序，互斥管独占。
- 死锁四条件：互斥、持有等待、不可抢占、循环等待。
- 虚拟内存靠页表映射，TLB 加速地址转换。
- 缺页中断会带来高成本。
- 栈自动管理，堆手动或由 RAII 管理。
- epoll 适合大量连接少量活跃场景。
- 定位问题先看现象、范围、数据，再提出假设并验证。

## P0：必须优先掌握

### 1. 进程和线程有什么区别？

进程是资源隔离和管理的容器，线程是进程内部实际执行指令的执行流，也是操作系统进行调度的基本对象之一。一个进程至少有一个线程。

| 对比项 | 进程 | 线程 |
|---|---|---|
| 地址空间 | 通常独立，彼此隔离 | 同一进程内共享地址空间 |
| 主要资源 | 地址空间、句柄/描述符、映射、权限等 | 栈、寄存器、程序计数器、线程局部存储 |
| 创建和切换 | 通常更重 | 通常更轻，但仍有内核调度和栈空间成本 |
| 通信 | 需要 IPC，边界清晰 | 可直接访问共享内存，通信快但要同步 |
| 故障影响 | 一个进程崩溃通常不直接破坏其他进程 | 未处理异常可能终止整个进程 |

**具体使用：** 将不可信模块、插件或需要独立升级的服务拆成进程，利用隔离降低故障传播；将同一服务内的并行计算、后台 IO、任务队列消费者设计为线程。进程间通信通常需要管道、socket 或共享内存，线程间则经常使用 mutex、原子变量和条件变量。

**边界和问题：** “线程切换一定比进程切换快”不是绝对结论，切换成本还与地址空间切换、缓存、调度状态和平台实现有关；线程过多会增加栈内存、上下文切换和锁竞争。多线程共享数据虽然快，但数据竞争、死锁和悬空引用会让问题更难定位。

面试表达：

> 进程更强调资源隔离，线程更强调执行流。选择进程还是线程，实际是在隔离性、通信成本、故障范围和并发效率之间做权衡。

### 2. 同一进程内线程共享什么，独占什么？

共享：代码段、全局变量、静态变量、堆、内存映射、打开的文件描述符或句柄，以及进程的地址空间和大部分资源。

独占：线程栈、程序计数器、通用寄存器、调度状态、线程局部存储和线程标识。函数的局部变量通常在线程栈上，因此不同线程默认不会共享它们；如果局部变量里保存的是指针，指针指向的堆对象仍可能是共享的。

**具体使用：** 把只读配置放在共享区域，把可变状态封装后通过锁或原子操作访问；把每线程缓存、临时缓冲区放到线程局部存储，减少锁竞争。跨线程传递任务时，优先传递明确的所有权或值，而不是裸指针。

**常见问题：** 共享文件描述符并不等于读写操作天然安全；共享对象需要同时考虑数据竞争、生命周期和内存可见性。线程退出后，指向其栈变量的指针会失效；线程局部对象也有销毁时机和线程池复用带来的清理问题。

### 3. 协程和线程有什么区别？

线程通常由内核调度，协程通常由用户态运行时在遇到 `await`、显式 `yield` 或异步 IO 完成时切换。协程切换保存的是协程自己的执行状态，通常不需要完整地进入内核。

| 对比项 | 线程 | 协程 |
|---|---|---|
| 调度者 | 操作系统内核 | 用户态运行时或框架 |
| 并行 | 多核上可以真正并行 | 单个线程内不能并行，多个线程承载协程才可并行 |
| 阻塞影响 | 一个线程阻塞不一定影响其他线程 | 协程若执行阻塞调用，可能阻塞承载它的整个线程 |
| 适合场景 | CPU 任务、传统阻塞式代码 | 大量 IO 等待、异步流程编排 |

**具体使用：** 网络服务器可以用少量线程承载大量协程，把等待网络、定时器和文件操作转成异步挂起，从而降低线程数量。CPU 密集任务仍应放入线程池或专门的计算队列，不能指望协程自动获得并行能力。

**边界和问题：** 协程不是“更快的线程”；它依赖运行时、异步 API 和正确的取消/超时处理。一个协程执行长时间 CPU 计算或调用阻塞 API，会拖住同一调度器上的其他协程；协程栈、生命周期、异常传播和跨线程恢复也会增加调试复杂度。

### 4. 用户态和内核态是什么？为什么要区分？

用户态运行普通应用代码，受到地址访问和特权指令限制；内核态运行操作系统核心代码，可以管理页表、设备、中断和进程资源。二者通过硬件权限级别隔离，防止普通程序直接破坏内核或其他进程。

进入内核的典型路径包括系统调用、硬件中断和处理器异常。文件读写、创建线程、网络收发等操作通常会触发系统调用；缺页、除零、非法指令则属于异常。系统调用返回后，CPU 再回到用户态继续执行。

**具体使用：** 诊断性能时要区分用户态 CPU 和内核态 CPU。用户态高可能是业务循环或算法热点；内核态高可能是系统调用过多、网络包处理、锁竞争、自旋或驱动问题。Linux 的 `top`、`pidstat` 和 Windows 的 WPA 都能帮助区分。

**边界和问题：** “进入内核态就一定很慢”不准确，成本取决于调用类型、缓存和数据量；而且异步 IO、内存映射和系统调用批处理都能减少频繁往返。权限隔离能保护系统，但用户态与内核态之间的数据复制、校验和调度仍可能成为瓶颈。

### 5. 用户态和内核态切换为什么有开销？

一次切换可能涉及保存寄存器和返回状态、切换特权级、执行系统调用入口和参数检查；某些操作还会引起调度、锁竞争、缓存失效或地址转换相关开销。真正耗时的常常不是“切换”本身，而是内核要完成的 IO、内存管理或设备操作。

**具体使用：** 对小块数据频繁 `read/write` 时，可以批量读写、使用缓冲 IO、`readv/writev` 或 IO 多路复用；文件发送可评估 `mmap`、`sendfile`；大量连接则用事件驱动减少线程和阻塞等待。

**适用边界：** 减少系统调用不等于把所有数据都堆在用户态。批量过大可能增加延迟和内存峰值，零拷贝也受文件类型、设备、协议栈和平台支持限制；需要通过 trace 或 profiling 证明瓶颈确实在系统调用路径。

### 6. 并发和并行有什么区别？

并发表示一个时间段内有多个任务处于推进状态，任务可以交替执行；并行表示多个任务在同一时刻由不同执行单元真正同时执行。单核可以并发，多核才有机会并行。

**具体使用：** IO 密集型程序用并发隐藏等待时间；CPU 密集型程序用并行利用多核。前者重点控制阻塞和任务调度，后者还要考虑任务拆分、负载均衡、共享数据和缓存一致性。

**常见问题：** 并行度超过 CPU 核数后，额外线程可能只带来切换和竞争；共享计数器即使加锁也可能发生缓存行抖动。并发程序还要区分“线程安全”与“结果正确”：没有崩溃不代表时序和业务状态正确。

### 7. 什么是上下文切换？

上下文切换是 CPU 从一个可运行任务切换到另一个任务，保存当前任务的寄存器、程序计数器和栈指针，再恢复下一个任务状态的过程。线程因时间片耗尽、阻塞、被更高优先级任务抢占等原因发生切换。

**如何使用和判断：** 线程池中线程数过多、锁自旋、任务过碎都可能造成切换频繁。Linux 可观察 `pidstat -w`、`vmstat` 或 perf trace，Windows 可用 WPA 看调度事件。应把切换次数与吞吐量、延迟和 CPU 利用率一起看，不能只追求切换次数低。

**常见误区：** 上下文切换成本不是固定常数；缓存、NUMA、地址空间和是否发生调度都会影响结果。减少线程数量也可能使 IO 等待无法被隐藏，因此线程池大小应结合 CPU 核数、阻塞比例和任务粒度压测确定。

### 8. 进程调度算法有哪些？

| 算法 | 机制和优点 | 主要问题 |
|---|---|---|
| FCFS | 按到达顺序执行，简单 | 长任务会阻塞后面的短任务 |
| SJF/SRTF | 优先运行短任务，平均等待时间较低 | 需要估计运行时间，长任务可能饥饿 |
| RR | 按时间片轮转，响应较公平 | 时间片过小切换多，过大又接近 FCFS |
| 优先级调度 | 重要任务优先 | 低优先级任务可能饥饿，需要老化或优先级继承 |
| 多级反馈队列 | 根据行为动态调整队列，兼顾响应和吞吐 | 参数多，行为复杂 |

现代操作系统通常使用更复杂的公平调度、优先级和实时调度策略，面试不应把课本算法直接等同于某个具体内核实现。调度的核心是平衡吞吐量、响应时间、公平性、实时性和功耗。

**具体使用：** 交互线程要避免被长时间计算占用；实时任务关注最坏响应时间；后台批处理关注吞吐量。优先级提升只能解决调度顺序，不能修复锁竞争、阻塞 IO 或算法本身过慢。

### 9. 同步和互斥有什么区别？

互斥解决“同一时刻不能有多个执行流进入临界区”，同步解决“多个执行流按什么条件或顺序推进”。例如多个线程写同一个容器需要互斥，生产者写入数据后通知消费者则是同步。

**具体使用：** 用 mutex 保护不变量和共享数据；用条件变量等待“队列非空”等谓词；用信号量表示可用资源数量；用原子变量处理简单计数、状态发布或无锁算法中的同步。

**核心注意：** 互斥并不自动保证业务正确，锁保护范围必须覆盖完整的不变量；同步也不等于休眠等待，忙等会消耗 CPU。条件变量必须在锁保护下检查谓词，并使用循环检查，以处理虚假唤醒和通知早于等待的问题。

### 10. `mutex`、`semaphore`、`condition_variable` 分别解决什么问题？

| 机制 | 核心语义 | 适合场景 | 常见坑 |
|---|---|---|---|
| mutex | 同一时刻一个持有者进入临界区 | 保护共享数据和不变量 | 临界区太大、锁顺序不一致、持锁 IO |
| semaphore | 一个可增减的许可计数器 | 连接数、缓冲区槽位、资源池 | 计数与实际资源状态不一致，忘记释放 |
| condition variable | 睡眠等待谓词，条件变化后被通知 | 生产者-消费者、状态变更 | 必须配 mutex，必须循环检查谓词 |

`condition_variable` 本身不保护数据；正确模式是“加锁、检查条件、条件不满足就等待，被唤醒后重新加锁并再次检查”。`notify` 只是提示状态可能变化，不是把条件永久保存成一个事件。

**适用边界：** 只有一个布尔状态时，原子变量可能比信号量更直接；资源数量和所有权复杂时，单纯用信号量容易出现泄漏和错配，应让资源池封装获取与归还。

### 11. 死锁是什么？四个必要条件是什么？

死锁是多个执行流永久等待，系统中每个参与者都无法继续推进。经典四个必要条件是：互斥、持有并等待、不可抢占、循环等待。四者同时成立才可能形成死锁，破坏任意一个条件就能从结构上避免它。

**具体判断：** 先画出“线程 -> 等待的锁”和“锁 -> 当前持有线程”的关系，再看是否存在环。例如线程 A 持有 `L1` 等 `L2`，线程 B 持有 `L2` 等 `L1`，就是典型等待环。

**边界和问题：** 死锁不只发生在 mutex，也可能发生在文件锁、数据库事务、线程 join、消息队列和跨进程资源上。活锁是线程不断重试但没有进展，饥饿是某线程长期得不到资源，三者要和死锁区分。

### 12. 如何避免和定位死锁？

常用治理方法：

- 为所有锁建立全局顺序，按顺序加锁，破坏循环等待。
- 尽量一次取得所需资源，或使用 `std::lock`/`scoped_lock` 统一加多个锁。
- 缩小临界区，禁止持锁执行磁盘、网络、外部回调和未知代码。
- 使用 RAII 确保异常和提前返回路径释放锁；必要时使用超时锁记录诊断信息。
- 设计锁的所有权和层级，避免在析构、回调或日志路径中隐式重新加锁。

定位时先冻结现场，查看所有线程栈，再建立锁等待图，确认“谁持有、谁等待、等待了多久”。Windows 可用 WinDbg 的线程和同步对象信息，Linux 可用 gdb、`pstack`、perf 或锁竞争分析工具。

**注意：** `try_lock` 失败后无限重试可能变成活锁；超时只能让问题暴露或降级，不能替代正确的锁顺序。生产环境应记录锁等待耗时和线程信息，否则偶发死锁通常只能靠猜。

### 13. 什么是虚拟内存？

虚拟内存为每个进程提供独立的虚拟地址空间。CPU 生成虚拟地址，MMU 按页表将其转换为物理地址，并根据页表权限检查读、写和执行权限。

**具体作用：** 实现进程隔离和内存保护；支持按需分页、写时复制和共享库；让程序不必关心物理内存的连续布局；通过内存映射把文件或设备映射到地址空间。

**不要混淆：** 虚拟地址空间大，不代表已经占用了同样大小的物理内存。排查内存时要区分虚拟地址保留、已提交内存、驻留集/工作集、共享页和私有脏页。过度提交还可能导致分配成功但后续访问时内存压力或 OOM。

### 14. 虚拟地址如何映射到物理地址？

虚拟地址通常拆成虚拟页号和页内偏移。MMU 先查 TLB；命中时得到物理页号，再与偏移组合成物理地址。TLB 未命中时，硬件或内核遍历多级页表；若页表项显示页面不在内存或权限不允许，则触发缺页异常。

**核心机制：** 多级页表通过按需分配页表降低空间开销；大页可以减少 TLB 压力，但会增加内存占用和内部碎片。进程切换可能影响 TLB，有些平台通过地址空间标识减少刷新成本。

**常见问题：** TLB miss 不等于缺页，前者只是缓存未命中，通常仍可从页表找到映射；缺页也不一定是磁盘 IO，可能只是首次分配、写时复制或权限检查失败。回答时应区分这两种成本。

### 15. 什么是缺页异常？

进程访问的虚拟页没有当前有效的物理映射，或访问权限不满足时，CPU 会陷入内核处理。处理结果可能是建立映射、从后备存储换入、分配新页，也可能判定为非法访问并终止进程。

常见情况：按需加载代码或数据、换入被回收的页面、写时复制、栈自动增长、访问空指针或越界地址。

**具体排查：** 少量缺页是正常的按需加载；持续大量 major fault 往往伴随磁盘 IO 和延迟升高，可能导致抖动。排查时看 minor/major fault、工作集、内存回收、IO 延迟和访问模式，不能看到“缺页”就直接认定为 bug。

### 16. 堆和栈有什么区别？

栈保存函数调用帧、返回地址和通常的局部变量，由线程创建时建立并随调用自动伸缩；堆由分配器动态管理，适合跨函数、跨线程或不确定生命周期的对象。堆对象的实际管理者仍应由明确的所有权类型承担。

**具体使用：** 小型、短生命周期、不会逃逸的对象可以放栈上；需要动态生命周期的对象使用 `std::unique_ptr`、`std::shared_ptr` 或容器。大数组、深递归不要放栈上；高频小对象分配可考虑对象池，但要评估内存占用、线程安全和碎片。

**常见问题：** 栈溢出通常来自深递归或超大局部变量；堆问题包括泄漏、重复释放、悬空指针、越界和碎片。RAII 能管理资源生命周期，但不能防止数组越界或数据竞争，仍需 sanitizer、静态分析和边界检查。

## P1：工程常问，体现排障能力

### 17. 进程间通信方式有哪些？

| 方式 | 机制和使用 | 适用边界与问题 |
|---|---|---|
| 匿名管道 | 内核缓冲区，常用于有亲缘关系进程的简单字节流 | 方向和容量有限，不适合复杂协议 |
| 命名管道 | 通过系统命名对象连接无亲缘进程 | 本机通信方便，跨平台和跨机器能力有限 |
| 消息队列 | 内核保存带边界的消息，可按类型或优先级取消息 | 有内核拷贝和容量限制，消息过大不合适 |
| 共享内存 | 多个进程映射同一物理页 | 吞吐高，但必须自行处理同步、布局和崩溃恢复 |
| 信号/事件 | 传递“发生了某事”的通知 | 携带数据少，不能替代可靠消息队列 |
| socket | 字节流或报文通道，可本机或跨机器 | 协议、序列化、半包、超时和断连需自行设计 |

**选择思路：** 小数据、简单父子通信选管道；需要消息边界和异步消费选消息队列；大吞吐、低延迟选共享内存并配合信号量或事件；需要跨机器或独立部署选 socket。IPC 的性能不仅由复制次数决定，还取决于序列化、唤醒、锁和协议处理。

### 18. 共享内存为什么快？为什么还需要同步？

多个进程把同一物理内存页映射到各自的虚拟地址空间，读写数据时不必经过“进程 A 用户态 -> 内核 -> 进程 B 用户态”的反复复制，因此适合大块数据和高吞吐场景。

它只解决“数据放在哪里”，不解决“谁先读写”和“什么时候数据完整”。生产者写入索引和内容的顺序、消费者读取的可见性、环形队列的并发更新都需要同步协议。

**具体使用：** 共享内存环形队列常用生产者/消费者索引、原子变量、内存序和事件通知。跨进程锁还要考虑进程崩溃后锁是否能恢复、结构体布局是否稳定、不同进程是否使用相同的对齐和版本。

**常见问题：** 共享内存不是天然“零成本”：仍可能发生缓存一致性流量、伪共享、页缺失和同步唤醒。只读共享通常简单；多写者场景若没有清晰的所有权协议，往往比 socket 更难维护。

### 19. `select`、`poll`、`epoll` 有什么区别？

| 机制 | 核心机制 | 适用边界 |
|---|---|---|
| `select` | 每次把 fd 集合传给内核，返回后线性扫描；集合大小通常有限 | 连接数少、兼容性要求高 |
| `poll` | 用数组/结构体传递 fd，突破固定数量限制，但仍线性扫描 | 中小规模连接，代码简单 |
| `epoll` | 用 `epoll_ctl` 维护内核关注集合，`epoll_wait` 主要返回就绪事件 | Linux 大量连接且同时活跃连接较少 |

`epoll` 的优势不是“永远是 O(1)”或“任何场景都快”，而是避免每次调用都重复传递和扫描全部关注 fd。在大量连接同时活跃时，事件处理本身仍可能接近线性；跨平台程序还要考虑 BSD 的 kqueue、Windows 的 IOCP 等模型。

**使用要点：** socket 设为非阻塞；正确处理读到 0、`EAGAIN`、错误和半包；限制单个连接一次处理的预算，防止一个活跃连接饿死其他连接。

### 20. `epoll` 的 LT 和 ET 有什么区别？

水平触发 LT 是“条件仍成立就继续通知”：只要接收缓冲区还有数据，下一次等待仍可能返回该 fd。边缘触发 ET 是“状态发生变化时通知”：从不可读变为可读时通知，之后必须主动把数据读到 `EAGAIN`。

**具体使用：** LT 容错性高、代码简单，适合大多数业务；ET 能减少重复通知，适合高性能事件循环，但要求所有 fd 非阻塞，并在一次事件中循环读写直到暂时无数据。

**常见问题：** ET 下只读一次会留下数据却没有下一次边沿，表现为连接“卡住”；忽略写缓冲区满会丢数据或忙等；关闭和错误事件必须统一清理。ET 不是自动更快，系统瓶颈在业务处理时通常收益很小。

### 21. 什么是零拷贝？

零拷贝是减少数据在用户态和内核态之间复制或减少 CPU 参与的统称，并不意味着物理内存中完全没有任何复制。传统文件发送可能经历页缓存、用户缓冲区、socket 缓冲区和网卡 DMA 等多个阶段。

常见机制包括 `mmap`、`sendfile`、`splice`、DMA、`io_uring` 等。它们可能减少用户态复制、系统调用次数或 CPU 拷贝，但具体收益取决于内核、文件系统、网卡和数据路径。

**适用场景：** 大文件顺序发送、网关转发、日志搬运等“数据不需要在用户态修改”的场景更适合。需要解压、加密、协议解析或按字段改写时，数据仍然要进入用户态，零拷贝收益会下降。

**不足：** 映射大文件可能增加地址空间和缺页压力；`sendfile` 对目标类型有约束；减少复制后排查和生命周期管理更复杂。应通过 CPU、内存带宽、吞吐和延迟基准测试确认收益。

### 22. CPU 负载过高如何定位？

先确认指标含义：load average 包含可运行任务和部分不可中断等待，不能简单等同于 CPU 使用率。然后按“范围 -> 进程 -> 线程 -> 栈/热点 -> 假设 -> 验证”推进：

1. 确认是整机、容器、某进程还是某线程异常，并观察持续时间和复现条件。
2. 找出高 CPU 线程，区分用户态、内核态、iowait、软中断和 steal 等来源。
3. 用采样 profiler 或线程栈判断是死循环、算法热点、锁自旋、频繁分配、系统调用还是日志过多。
4. 对照发布记录、输入规模和请求量做实验，修复后用同一指标回归。

Linux 可组合 `top`、`pidstat -u -t`、`perf top/record`、`strace -c`；Windows 可使用任务管理器、Process Explorer、WPR/WPA 和 Visual Studio Profiler。

**常见误区：** 进程 CPU 低不代表没有问题，可能是主线程阻塞或某个线程短时尖峰；`strace`/调试器本身有开销，不能把工具观测到的行为直接当作原始行为。优化前先采样，不要凭代码阅读猜热点。

### 23. 程序卡顿如何定位？

先定义卡顿：哪个用户动作、从什么时候开始、持续多久、影响哪些线程和用户。然后同时收集时间线和现场栈，重点检查：

- UI/主线程是否在等待锁、同步 IO、网络、磁盘或子进程；
- 是否被长任务、频繁内存分配、缺页或高 CPU 抢占；
- 消息循环、事件循环或协程调度器是否被阻塞；
- 后台线程是否通过同步回调反向等待主线程；
- 是否存在队列堆积、优先级反转或单个任务处理过久。

**具体方法：** Windows 客户端可用 WPR/WPA、WinDbg 或 ETW 记录线程状态、磁盘和 UI 事件；Linux 可用 perf、trace、gdb 和 IO 工具。短卡顿看时间线，长时间卡死看所有线程栈和等待关系。

**边界：** “主线程 CPU 高”与“主线程在等 IO”处理方式完全不同；增加线程不能解决主线程必须串行更新 UI 的问题，异步化也不能掩盖未处理的取消、顺序和错误传播。

### 24. 死锁如何定位？

定位不是只看一个卡住的线程，而是还原整个等待图：

1. 获取所有线程的栈和状态，不要只看当前线程。
2. 识别每个线程正在等待的锁、事件、条件变量、`join`、IO 或消息。
3. 找到对应资源的持有者，记录持有时间和调用位置。
4. 画出线程与资源的边，检查是否有环，并核对实际加锁顺序。
5. 结合源码检查异常、回调、析构和超时路径是否会跳过释放。

Linux 常用 gdb、`pstack`、perf 和锁竞争工具；Windows 常用 WinDbg 的线程/等待信息、`!analyze`、`~* k` 等命令以及 WCT/ETW。拿不到现场时，应增加锁等待日志、线程 ID、资源 ID 和超时转储，否则只能依赖复现。

## P2：补充广度

### 25. 局部性原理是什么？

时间局部性是刚访问的数据短时间内可能再次访问；空间局部性是访问一个地址后，附近地址也可能被访问。CPU cache、TLB、硬件预取、分页和文件缓存都利用了局部性。

**具体使用：** 连续遍历 `vector` 往往比随机访问链表更缓存友好；按块处理矩阵、批量读取和对象池都可能改善局部性。优化时应看 cache miss、分支和内存带宽，而不是凭“连续内存一定快”下结论。

**边界：** 数据很大或访问随机时，预取可能无效甚至浪费带宽；过度追求局部性可能增加代码复杂度。多线程共享同一缓存行还会造成伪共享，即逻辑上不共享的数据仍反复触发缓存一致性通信。

### 26. 页面置换算法有哪些？

发生缺页且内存紧张时，系统需要选择一个页面换出。理想算法知道未来访问序列，实际只能用近似策略：

- FIFO：淘汰最早进入的页面，开销低，但可能淘汰仍热门的页面，甚至出现 Belady 异常。
- LRU：淘汰最近最少使用页面，符合局部性，但精确维护访问顺序成本高。
- LFU：淘汰访问次数最低的页面，适合长期频率明显的场景，但旧热点可能长期占据内存，且计数维护有开销。
- Clock/Second Chance：利用访问位近似 LRU，维护成本较低，是常见工程折中。

这里的页面置换是操作系统层面的抽象，不应简单理解成每次缺页都同步读取磁盘；现代系统还会使用工作集、预取、回收和文件缓存策略。频繁置换导致抖动时，应先检查工作集是否超过可用内存和访问模式，而不是只更换算法名称。

### 27. 内部碎片和外部碎片是什么？

内部碎片是已经分配给对象的块内部没有使用的空间，例如按固定大小或对齐分配；外部碎片是空闲空间分散成许多小块，虽然总空闲量够大，却无法满足连续大块申请。

**具体使用：** 分页和固定大小分配更容易出现内部碎片；需要连续可变大小内存的分配器容易出现外部碎片。现代堆分配器通常用 size class、空闲链表、合并和分区等方法折中。

**排查注意：** 进程“申请失败”不一定是外部碎片，也可能是地址空间限制、提交额度、容器限制或单次申请过大。要结合分配器统计、虚拟地址布局、驻留内存和进程限制判断。

### 28. 常用 Linux 命令如何用于排查？

| 命令 | 具体用途 | 使用注意 |
|---|---|---|
| `top`/`htop` | 看整体负载、CPU、内存和线程 | 先按线程观察，注意采样间隔 |
| `ps -ef`/`ps -L` | 查看进程、线程、启动参数 | 结合 PID 和时间点记录现场 |
| `pidstat` | 观察进程/线程 CPU、IO、上下文切换 | 适合持续采样比较趋势 |
| `free`/`vmstat` | 看内存、回收、换页和运行队列 | 不要只看 free，关注 available 和 swap |
| `ss`/`lsof` | 查连接、端口、文件描述符 | 区分监听、已连接和大量半连接 |
| `strace -p` | 跟踪系统调用和阻塞位置 | 有侵入性，短时间采集 |
| `pstack`/`gdb` | 获取线程栈和现场变量 | attach 可能暂停或影响进程 |
| `perf` | 采样 CPU 热点、调用图、调度事件 | 需要权限和符号，解释采样偏差 |
| `df`/`du` | 区分文件系统容量和目录占用 | 删除但仍被进程打开的文件要另查 |

正确做法是先定义假设，再选择最小工具集采样，保留命令、时间、版本和结果。单个命令的瞬时输出不能证明因果关系。

### 29. WinDbg 在异常和死锁分析中看什么？

崩溃分析先确认 dump 类型、架构和符号是否匹配，再看异常码、异常地址、故障线程调用栈、寄存器、模块版本和参数。常用思路是先用 `!analyze -v` 获得线索，再用 `k`/`~* k`、模块和源代码信息验证，不要把自动分析结果当成最终结论。

卡死或死锁分析重点看所有线程：哪些线程在等待、等待对象是什么、锁由谁持有、持有线程又在等待什么。必要时结合 `!locks`、线程环境块、事件/互斥体信息和 ETW/WCT 还原等待链。

**适用边界和问题：** 没有正确 PDB 时，调用栈可能只有地址，优化和内联也会让栈看起来不完整；minidump 可能缺少堆或句柄信息，无法回答所有问题。分析结果必须结合版本、日志、复现条件和源码验证。对生产进程 attach 可能改变时序，应优先分析 dump 或 trace。
