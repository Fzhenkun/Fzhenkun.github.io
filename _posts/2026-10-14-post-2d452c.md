> 本方案面向 Windows 桌面端软件，覆盖 C/C++ 原生程序、Electron/WebView 容器、混合架构以及多进程客户端。
> 目标是把“出了问题再排查”建设为一套可持续运行的工程系统：问题可观测、现场可捕获、原因可定位、风险可止损、版本可验证。

## 一、目标与适用范围

### 1.1 建设目标

稳定性建设关注“软件是否持续正确地工作”，性能建设关注“软件在可接受资源成本内完成工作”。两者不能割裂：

- 卡顿可能最终表现为崩溃、超时或用户强制退出；
- 内存、CPU、文件 IO 和网络 IO 的失控会放大稳定性风险；
- 没有现场数据的稳定性指标只能告诉我们“发生了什么”，不能回答“为什么发生”；
- 没有版本基线的性能数据无法判断优化是否有效，也无法阻止回归。

建设目标应落到以下闭环：

```text
定义用户场景
  -> 建立指标和基线
  -> 采集事件与现场
  -> 聚合、归因、定位
  -> 修复、优化、降级或回滚
  -> 版本准出和持续回归
```

### 1.2 关注对象

| 类别 | 典型问题 | 主要结果 |
| --- | --- | --- |
| 稳定性 | 崩溃、OOM、卡顿、卡死、白屏、黑屏、启动失败、异常退出 | 用户无法继续使用或数据丢失 |
| 性能 | 启动慢、交互耗时、CPU 高、内存增长、GPU 高、IO 阻塞、网络慢 | 用户感知变差、设备资源被挤占 |
| 工程能力 | 日志缺失、符号不匹配、无法复现、告警失效、无法回滚 | 定位和恢复成本过高 |
| 运行环境 | Windows 版本、驱动、安全软件、输入法、第三方注入、硬件差异 | 同一版本在不同设备表现不同 |

### 1.3 非目标

本方案不替代具体业务的容灾设计、服务端 SLO、网络协议设计或安全合规制度。它提供桌面端客户端侧的通用工程基线；具体阈值应结合业务重要性、用户画像和最低支持环境确定。

## 二、核心理论与设计原则

### 2.1 四阶段模型：观测、分析、治理、预防

这是整个体系的主线：

1. **观测**：采集事件、指标、日志、调用栈、Dump、环境画像和用户操作上下文。
2. **分析**：按版本、设备、系统、功能和时间聚合，结合调用栈、ETW Trace、日志和代码定位原因。
3. **治理**：修复代码，优化资源使用，增加超时、取消、重试、降级、隔离和恢复策略。
4. **预防**：静态检查、代码审查、自动化测试、性能基线、灰度发布、告警和版本准入。

### 2.2 可观测性三要素

建议把客户端可观测性拆为：

- **Metrics**：回答“发生了多少、影响了多少用户、趋势如何”；
- **Logs**：回答“关键业务步骤走到了哪里、失败原因是什么”；
- **Traces/Profiles**：回答“时间和资源消耗在哪里、调用链和线程状态是什么”。

三者应使用相同的关联字段，例如 `app_version`、`build_id`、`session_id`、`event_id`、`scene` 和 `device_id_hash`，使单个事件可以从指标下钻到日志和现场。

### 2.3 可靠性工程的几个经典原则

#### 预防优先，但允许失败

不能假设网络、磁盘、驱动、权限、内存和第三方模块永远正常。对预期失败设计明确结果：

- 有界超时；
- 可取消；
- 有限重试和退避；
- 幂等操作；
- 降级或跳过非核心功能；
- 用户可理解的错误提示；
- 失败后可恢复或可重启。

#### 故障隔离和最小爆炸半径

把高风险、可重启、资源消耗大的能力放在独立进程或独立任务边界内。主进程不应因为渲染进程、插件、下载器、解码器或 GPU 进程失败而整体退出。

#### 以用户场景和分位数衡量

平均值容易掩盖长尾。启动、交互、文件打开、搜索、渲染和退出等场景应关注 `P50/P75/P95/P99`，并同时看失败率、影响用户数和问题持续时长。

#### 优化必须基于测量

性能问题先建立基线，再采样、定位、修改、复测。没有证据的“优化”可能只是增加复杂度，甚至使问题转移到其他线程或其他设备。

### 2.4 C++/Windows 调用栈理论的工程含义

Windows x64 ABI 规定参数主要通过 `RCX/RDX/R8/R9` 传递，调用者为被调函数预留 32 字节 shadow space，栈需要满足对齐要求。函数调用通过返回地址、栈帧和展开信息形成可回溯的调用链。

但发布版本会发生内联、尾调用、寄存器分配、帧指针省略和函数合并，因此：

- 调用栈不是源码调用图的完整复制；
- `/Od` 下看到的栈不能直接代表 `/O2` 线上行为；
- 真实发布编译选项必须纳入符号化和现场验证；
- x64、x86、ARM64 必须分别验证 `CONTEXT` 和栈回溯；
- 符号文件必须与 PE 模块严格匹配。

## 三、总体架构

### 3.1 分层架构

```text
┌──────────────────────────────────────────────────────────┐
│ 业务场景层：启动、登录、打开文件、搜索、编辑、导出、退出 │
├──────────────────────────────────────────────────────────┤
│ 观测层：指标、结构化日志、Trace、心跳、异常事件          │
├──────────────────────────────────────────────────────────┤
│ 现场层：崩溃上下文、调用栈、Dump、卡顿快照、资源快照       │
├──────────────────────────────────────────────────────────┤
│ 诊断层：符号化、聚合、ETW/WPA、日志关联、问题归因          │
├──────────────────────────────────────────────────────────┤
│ 治理层：修复、优化、降级、隔离、重启、回滚、用户提示        │
├──────────────────────────────────────────────────────────┤
│ 预防层：静态扫描、测试、性能基线、灰度、告警、准出          │
└──────────────────────────────────────────────────────────┘
```

### 3.2 事件统一模型

所有稳定性和性能事件至少包含：

```json
{
  "event_type": "crash|jank|oom|startup|operation|resource",
  "event_id": "uuid",
  "app_version": "1.0.0",
  "build_id": "release-build-id",
  "architecture": "x64",
  "scene": "startup",
  "process_role": "main|renderer|worker|watchdog",
  "session_id": "opaque-id",
  "timestamp": "UTC timestamp",
  "duration_ms": 123,
  "device_profile": {},
  "payload": {}
}
```

采集内容应遵循最小化原则：不上传用户文件内容、完整命令行、绝对路径中的用户名、业务密钥和不必要的堆内存；设备标识应哈希或使用不可逆匿名标识。

## 四、稳定性建设

### 4.1 崩溃

#### 指标

- 进程崩溃率：崩溃次数 / 活跃用户数或进程运行次数；
- 崩溃用户率：发生崩溃的设备数 / 活跃设备数；
- 主进程崩溃率、子进程崩溃率；
- 启动阶段崩溃率、核心功能崩溃率；
- 新增问题数、版本回归数、Top 问题影响用户数。

分母必须固定并写入指标口径。一般同时保留事件维度和用户维度，避免同一设备反复崩溃把影响范围误判为用户规模。

#### 捕获和诊断

推荐两级链路：

1. **默认轻量链路**：异常码、版本、线程角色、模块身份、`模块名 + RVA` 调用栈、资源快照和关键日志；
2. **疑难问题链路**：按采样、白名单或用户授权上传 MiniDump，使用 WinDbg/DbgEng 深度分析。

崩溃回调应尽量短小，不做网络请求，不执行复杂业务逻辑。现场采集失败时降级为：

```text
完整符号栈
  -> 模块 + RVA 栈
  -> 当前 PC、异常码、线程 ID
  -> 仅上报版本和崩溃元数据
```

#### Windows 实现要点

- 使用 SEH/未处理异常过滤器捕获异常上下文；
- 生成 Dump 时使用 `MiniDumpWriteDump`，并用进程级锁保护 DbgHelp；
- 记录异常代码、异常地址、故障线程、加载模块和采集阶段；
- 不把 `SetUnhandledExceptionFilter` 当作唯一保障，应兼容 WER、Crashpad 或现有崩溃基建；
- 对 `EXCEPTION_STACK_OVERFLOW`、堆损坏、Loader Lock 等异常保留“采集可能失败”的预期；
- 退出崩溃、主动退出和更新重启要有明确区分。

### 4.2 卡顿与卡死

#### 定义

卡顿是线程在超过场景阈值的时间内没有完成预期进度；卡死是卡顿后在观察窗口内没有恢复。不要只用一次超时把所有问题标为卡死。

建议采用 watchdog 心跳：

```text
被观测线程定期更新心跳
观察线程检查最后心跳时间
超过阈值 -> 记录 jank 开始
恢复心跳 -> 记录恢复时长
持续无心跳 -> 记录 hang，并执行止损策略
```

应区分 UI 消息线程、渲染线程、IPC 线程、下载线程和业务主线程。UI 线程卡顿不等价于整个进程 CPU 高；CPU 低也不代表没有卡死，线程可能在锁、IO 或系统调用上等待。

#### 采集风险

同进程 `SuspendThread` 获取现场可能因目标线程持有堆锁、Loader Lock 或业务锁而造成采集器自死锁。生产环境优先使用独立 watchdog 进程：

```text
watchdog.exe
  -> 监控主进程心跳/IPC
  -> 获取目标线程和上下文
  -> 在隔离进程中采集调用栈或生成 Dump
  -> 超时退出并保证目标进程可恢复
```

所有挂起路径都必须保证恢复线程、关闭句柄和超时退出。

### 4.3 OOM 与内存泄漏

#### 指标

- 工作集、Private Bytes、Commit、虚拟地址空间；
- 进程级和子进程级内存分位数；
- 启动后、核心操作后、空闲 5/15/30 分钟后的内存水平；
- OOM 率、分配失败次数、单次大分配次数；
- 缓存大小、对象数量、句柄数量、GDI/User 对象数量；
- 长时间运行后的增长斜率，而不仅是单点峰值。

#### 治理原则

- 设置缓存上限和淘汰策略；
- 避免大对象重复拷贝和 IPC 反序列化膨胀；
- 大文件使用流式处理，不一次性加载；
- 非核心资源在内存压力下主动释放；
- 对异常路径和重试路径检查资源是否重复持有；
- 使用 RAII、所有权明确的智能指针和句柄封装；
- 对加载插件、图片、媒体和 Web 内容设置隔离与回收策略。

内存指标必须关联设备内存容量、系统剩余内存和版本，否则无法区分软件自身增长与系统整体资源紧张。

### 4.4 异常、启动失败、白屏和黑屏

把核心路径拆成可观测阶段：

```text
进程创建
 -> 配置加载
 -> 依赖检查
 -> 窗口创建
 -> 渲染器启动
 -> 首屏可见
 -> 首次可交互
 -> 核心数据加载完成
```

每个阶段记录成功、失败、耗时和错误码。对于 WebView/Electron：

- 区分主进程异常、Renderer 崩溃、页面 JS 异常和网络失败；
- 上报 `uncaughtException`、`unhandledRejection` 和 source map 版本；
- 监控页面首个可见元素、渲染提交和首次可交互；
- GPU 进程失败时提供软件渲染或功能降级；
- 白屏/黑屏检测应结合页面状态、可见元素和渲染结果，不能仅以 DOM 加载完成判断。

## 五、性能建设

### 5.1 性能指标设计

| 场景 | 推荐指标 | 诊断信号 |
| --- | --- | --- |
| 启动 | 冷启动/热启动、首窗、首屏、首次可交互 P50/P95 | 磁盘 IO、依赖加载、初始化串行化 |
| 交互 | 点击到反馈、输入延迟、菜单/搜索/切换耗时 | UI 线程阻塞、同步 IPC、布局和绘制 |
| 文件 | 打开、保存、导入、导出耗时 | 文件大小、HDD/SSD、杀毒拦截 |
| 网络 | DNS、连接、首包、下载、解析、渲染 | 延迟、丢包、重试、并发和响应体积 |
| 渲染 | 帧耗时、丢帧率、GPU 使用、纹理/显存 | 过度绘制、大纹理、驱动兼容 |
| 资源 | CPU、内存、句柄、磁盘占用 | 泄漏、缓存无界、忙等、碎片化 |

耗时类指标优先使用分位数；资源类指标同时记录峰值、平均值、分位数和持续时间占比。

### 5.2 CPU

优化步骤：

1. 先通过任务管理器、Process Explorer 或 ETW 确认是进程、线程还是系统资源问题；
2. 用 WPR/ETW 采集实际场景；
3. 在 WPA 的 `CPU Usage (Sampled)` 或精确 CPU 视图中按进程、线程和调用栈下钻；
4. 区分计算热点、忙等/轮询、频繁上下文切换、锁竞争和系统调用；
5. 修改后使用同设备、同数据集、同场景复测。

常见治理：

- UI 线程只做轻量、可快速完成的工作；
- 大计算拆分为可取消的后台任务；
- 消除固定周期忙轮询，优先使用事件、等待对象或消息；
- 减少锁粒度和锁持有时间，避免在锁内做 IO；
- 控制线程数量、任务队列长度和并发度；
- 对热点数据优化分配、拷贝、缓存局部性和算法复杂度。

### 5.3 文件 IO

文件 IO 是 Windows 桌面端卡顿的常见来源，尤其在机械硬盘、同步目录和安全软件拦截环境中。

- UI 线程禁止执行不可控的同步文件 IO；
- 合并小文件写入，设置日志滚动和总量上限；
- 使用临时文件加原子替换，避免写到一半留下损坏文件；
- 明确 `FlushFileBuffers` 的必要性和成本；
- 区分系统缓存命中和实际磁盘 IO；
- 使用 Procmon 定位路径、访问类型、耗时和拦截状态；
- 冷启动测试应定义缓存状态，否则测试结果不可比。

### 5.4 网络 IO

- 所有请求设置连接、读取和整体超时；
- 重试只用于可恢复错误，采用指数退避和最大次数；
- 业务操作保证幂等，避免重试造成重复提交；
- 对上传、下载和缓存设置并发、带宽和磁盘配额；
- 网络失败时区分离线、DNS、TLS、服务端错误和业务错误；
- 不在主线程同步等待网络；
- 将请求阶段耗时拆为 DNS、连接、TLS、首包、下载和解析。

### 5.5 内存、GPU 和磁盘占用

- 记录工作集与 Private Bytes，避免只看任务管理器的一个数字；
- 纹理、图片、视频和 Web 页面资源应设置尺寸、格式、缓存和生命周期上限；
- GPU 问题使用 WPR/WPA、GPUView 或框架自身工具定位；
- 安装包、安装目录、更新包、日志和缓存分别建立大小基线；
- 版本准入检查包体积增量，超过阈值必须说明原因；
- 磁盘剩余空间不足时提前提示、停止非必要缓存写入并保留核心功能。

## 六、Windows 现场采集与符号化

### 6.1 Dump 与轻量调用栈的组合策略

| 场景 | 推荐方案 | 原因 |
| --- | --- | --- |
| 高频崩溃/卡顿 | `模块 + RVA` 栈 | 小、快、便于跨平台批量聚合 |
| 低频疑难问题 | MiniDump | 保留寄存器、线程、内存和异常上下文 |
| 研发复现 | WinDbg/Visual Studio + PDB | 便于交互式深度分析 |
| 线上高敏感数据 | 轻量栈和脱敏日志 | 降低隐私和存储风险 |

两者不是互斥关系。轻量栈适合发现头部问题，Dump 适合解释复杂现场。

### 6.2 `模块 + RVA` 方案

ASLR 会改变模块绝对加载地址，因此不能上传绝对地址：

```text
RVA = PC - module_load_base
```

客户端上传：

```text
模块名!0xRVA
```

服务端根据 `release/build_id`、模块 CodeView 标识、PDB GUID/Age 或等价指纹，读取发布期生成的符号映射表。

发布流水线：

```text
编译 exe/dll + PDB
  -> 校验 PE 与 PDB 匹配
  -> 导出函数范围和源代码行
  -> 生成按版本归档的 map
  -> 上传符号存储
  -> 发布客户端
```

映射表至少包含：

```text
module_name
architecture
pe_identity
pdb_guid
pdb_age
function_rva
function_size
function_name
line_rva
source_file
line_number
```

服务端查找函数时使用：

```text
function_rva <= frame_rva < function_rva + function_size
```

函数表按起始 RVA 排序并二分查找。非首帧通常按 `RVA - 1` 进行源代码行映射，以便落在调用指令所在行。

### 6.3 符号化注意事项

- 符号不匹配时保留原始 `模块 + RVA`，不要丢弃整条调用栈；
- 系统模块和驱动模块通常只保留模块名与 RVA；
- 内联函数无法通过普通栈帧完整恢复；
- 尾调用、优化、异常展开信息会改变可见调用链；
- 采集器自身的栈帧应从聚合键中截断；
- 记录解析成功率、未知模块率和版本不匹配率；
- 不把完整 PDB 分发到客户端。

## 七、诊断工具链

### 7.1 常用工具

| 工具 | 适用问题 |
| --- | --- |
| Task Manager | 粗粒度 CPU、内存、磁盘、GPU、网络观察 |
| Process Explorer | 进程、线程、句柄、模块、CPU 和内存细节 |
| Procmon | 文件、注册表、进程和网络行为关联 |
| WPR | 采集 Windows ETW 性能 Trace |
| WPA | 分析 CPU、调度、IO、内存、启动和图形数据 |
| GPUView | GPU 队列、提交、调度和同步分析 |
| WinDbg/CDB | Dump、异常、线程、调用栈和内存分析 |
| ProcDump | 按崩溃、未响应、CPU 等条件捕获 Dump |
| Crashpad/Breakpad | 崩溃捕获、上报和符号化链路 |

### 7.2 标准诊断流程

1. 明确用户可感知现象和复现步骤；
2. 确认版本、系统、架构、设备、驱动和第三方注入环境；
3. 确认问题是稳定性、性能、资源还是兼容性；
4. 先看大盘趋势和分布，再看单个现场；
5. 对卡顿/耗时问题采集 ETW Trace；
6. 对崩溃/卡死问题解析调用栈或 Dump；
7. 将日志时间线、线程状态、资源曲线和调用栈关联；
8. 形成“证据、假设、验证、修复、回归”的问题记录；
9. 修复后做同场景对比和长时间稳定性验证。

### 7.3 问题归因分类

建议至少分为：

- 代码缺陷：空指针、越界、竞态、死锁、未定义行为、资源泄漏；
- 任务设计：大任务运行在 UI 线程、没有取消、没有超时；
- 资源问题：内存、CPU、GPU、磁盘、网络、句柄不足；
- 环境问题：系统版本、驱动、安全软件、输入法、第三方注入；
- 构建问题：符号缺失、依赖缺失、架构错误、安装包产物变化；
- 数据问题：异常数据量、超大文件、损坏缓存、脏配置；
- 产品策略问题：重试风暴、缓存无界、失败后没有恢复路径。

## 八、开发、测试与发布准入

### 8.1 开发阶段

- 结构化日志和错误码先于功能上线；
- 核心接口明确超时、取消、重试和错误传播策略；
- 资源使用采用 RAII 和所有权约束；
- C++ 启用编译器警告、静态分析、clang-tidy 或等价规则；
- 对跨 DLL、回调、C ABI、Windows API 和线程模型做接口约束；
- 关键路径增加可关闭的性能计时点；
- Code Review 必须检查异常路径和资源释放路径。

### 8.2 测试阶段

测试矩阵至少包含：

| 维度 | 样例 |
| --- | --- |
| 系统 | 最低支持版本、当前主版本、企业环境版本 |
| 架构 | x64、必要时 x86/ARM64 |
| 设备 | 低配、主流、高配；HDD/SSD；不同 GPU |
| 网络 | 正常、弱网、高延迟、丢包、断网恢复 |
| 数据 | 空数据、边界数据、超大文件、损坏缓存 |
| 环境 | 安全软件、输入法、多屏、高 DPI、代理、第三方注入 |
| 生命周期 | 冷启动、热启动、睡眠唤醒、锁屏解锁、升级回滚 |

稳定性测试包括长稳、重复操作、随机操作、故障注入、进程重启、网络切换和磁盘空间压力。C++ 项目应结合 ASan/UBSan 等适用的检测配置；线上发布版本不能只验证 Debug 或关闭优化的行为。

### 8.3 性能基线

每个核心场景建立基线：

```text
场景 -> 固定设备/数据/环境 -> 重复 N 次 -> 记录 P50/P95/P99
     -> CPU/内存/IO/GPU/网络 -> 和上一版本比较
```

建议将以下指标设置为准出项：

- 启动和核心交互耗时不得超过基线允许增量；
- 核心场景内存峰值和空闲回落符合基线；
- CPU 高占用持续时间不超过阈值；
- 包体、安装目录、缓存和日志增量有明确原因；
- 版本没有新增高严重度崩溃和卡死问题；
- 符号、日志、Dump 和回滚链路经过演练。

### 8.4 灰度与止损

发布必须支持：

- 按版本、用户群、设备、系统和功能开关灰度；
- 发现指标激增时暂停放量；
- 远程关闭高风险功能；
- 回滚或强制升级；
- 对单个子进程自动重启；
- 对不可恢复场景提示用户并保留现场；
- 形成客服和技术支持的标准诊断包。

告警条件建议分为：

- **新增**：出现新的问题指纹；
- **激增**：相比基线或环比显著增长；
- **出现即告警**：重点用户、灰度版本、核心功能出现单例也要关注。

## 九、指标口径与监控设计

### 9.1 通用公式

```text
PV = 问题发生次数 / 功能使用次数
UV = 受影响设备数或用户数 / 活跃设备数或用户数
持续时长占比 = 问题持续时长 / 功能使用时长
错误率 = 失败次数 / 尝试次数
```

对开区间长尾使用分位数；统计前排除负数、极大值、重复上报和不具备观测意义的样本。短生命周期进程要在退出前补采最终值，否则采样窗口会产生偏差。

### 9.2 设备画像

设备画像至少包括：

- Windows 版本和构建号；
- x64/x86/ARM64；
- CPU 型号、核心/线程；
- 内存容量和系统剩余内存；
- GPU 型号、驱动版本、实际使用 GPU；
- 磁盘类型、安装盘和缓存盘剩余空间；
- 屏幕数量、分辨率、DPI 和刷新率；
- 网络类型、延迟和代理状态；
- 第三方注入模块和安全软件信息（遵循隐私与授权要求）。

## 十、SMART 建设计划

以下计划以 6 周为默认周期，可按团队规模调整。

| 阶段 | 目标 | 必做任务 | 输出物 | 验收 |
| --- | --- | --- | --- | --- |
| 第 1 周 | 建立基线 | 梳理核心场景、进程、线程和支持环境；定义指标口径 | 场景清单、指标字典、设备矩阵 | 每个核心场景有负责人、分母和采集点 |
| 第 2 周 | 打通观测 | 接入结构化日志、启动/交互耗时、资源采样、错误码 | 客户端事件模型和基础看板 | 能按版本和设备下钻 |
| 第 3 周 | 打通现场 | 接入崩溃栈、卡顿心跳、Dump 兜底和符号归档 | 现场采集器、符号流水线 | 用测试故障验证端到端闭环 |
| 第 4 周 | 建立诊断 | 固化 WPR/WPA、Procmon、WinDbg 操作手册和问题模板 | 诊断手册、Top 问题列表 | 随机抽取问题可定位到模块/阶段 |
| 第 5 周 | 做治理 | 为核心异常增加超时、取消、降级、重启和回滚策略 | 故障策略清单、开关配置 | 故障注入后可恢复且有提示 |
| 第 6 周 | 接入准出 | 建立性能基线、灰度规则、告警和发布门禁 | 发布检查表、回归报告 | 版本可自动给出通过/阻塞结论 |

SMART 总目标：

- **S**：完成 Windows 桌面端核心场景的稳定性、性能和现场诊断闭环；
- **M**：核心场景 100% 有指标，崩溃/卡顿事件可关联版本和现场，发布版本具备性能基线和回滚能力；
- **A**：按上述 6 周拆分，每周交付可验证产物；
- **R**：直接服务于线上问题发现、定位、修复和版本准出；
- **T**：第 6 周结束完成首版闭环，之后按版本持续复盘。

## 十二、上线验收清单

### 观测

- [ ] 核心场景、核心路径和关键节点有明确指标；
- [ ] 指标分母、采样窗口、异常值处理和版本维度已定义；
- [ ] 日志包含错误码、阶段、耗时和关联 ID；
- [ ] 设备画像满足定位需要且符合隐私要求。

### 现场

- [ ] 崩溃可采集异常码、版本和调用栈；
- [ ] 卡顿有线程心跳、持续时长和恢复判断；
- [ ] Dump 兜底链路可用且有采样策略；
- [ ] 符号文件与发布产物一一对应；
- [ ] 符号缺失时仍保留原始模块 + RVA；
- [ ] x64、x86、ARM64 和真实优化配置已验证；
- [ ] 采集失败不会扩大故障或永久挂起线程。

### 性能

- [ ] 启动、核心交互、文件和网络场景有 P50/P95/P99 基线；
- [ ] CPU、内存、GPU、文件 IO、网络 IO 和磁盘有阈值；
- [ ] 关键耗时不在 UI 线程同步执行；
- [ ] 缓存、日志、并发、重试和队列有上限；
- [ ] 冷启动、弱网、低配设备和长稳场景已验证。

### 发布与运营

- [ ] 静态扫描、Code Review、自动化测试和性能回归已完成；
- [ ] 灰度、功能开关、暂停放量、回滚和强制升级可执行；
- [ ] 重点指标有告警和负责人；
- [ ] 客服/技术支持有标准诊断包和用户沟通话术；
- [ ] 已演练一次从发现、定位到止损的完整流程。
