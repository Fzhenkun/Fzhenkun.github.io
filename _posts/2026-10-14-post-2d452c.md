> 本方案面向 Windows 桌面端软件，覆盖 C/C++ 原生程序、Electron/WebView 容器、混合架构以及多进程客户端。
> 目标是把“出了问题再排查”建设为一套可持续运行的工程系统：问题可观测、现场可捕获、原因可定位、风险可止损、版本可验证。

## 一、目标与适用范围

### 1.1 建设目标

稳定性建设关注“软件是否持续正确地工作”，性能建设关注“软件在可接受资源成本内完成工作”。两者不能割裂：

- 卡顿可能最终表现为崩溃、超时或用户强制退出；
- 内存、CPU、文件 IO 和网络 IO 的失控会放大稳定性风险；
- 没有现场数据的稳定性指标只能告诉我们“发生了什么”，不能回答“为什么发生”；
- 没有版本基线的性能数据无法判断优化是否有效，也无法阻止回归。

建设目标应落到以下闭环：

```text
定义用户场景
  -> 建立指标和基线
  -> 采集事件与现场
  -> 聚合、归因、定位
  -> 修复、优化、降级或回滚
  -> 版本准出和持续回归
```

### 1.2 关注对象

| 类别 | 典型问题 | 主要结果 |
| --- | --- | --- |
| 稳定性 | 崩溃、OOM、卡顿/卡死、白屏、黑屏、启动失败、异常退出 | 用户无法继续使用或数据丢失 |
| 性能 | 启动慢、CPU 高、内存增长、GPU 高、IO 阻塞、网络慢 | 用户感知变差、设备资源被挤占 |
| 工程能力 | 日志缺失、符号不匹配、无法复现、告警失效、无法回滚 | 定位和恢复成本过高 |
| 运行环境 | Windows 版本、驱动、安全软件、输入法、第三方注入、硬件差异 | 同一版本在不同设备表现不同 |

### 1.3 保障环节

- 开发阶段：从源头上避免出现问题，对于预期内的问题设计应对策略（降级 fallback、自动恢复/主动重启、重试失败提示）
- 测试阶段：通过测试拦截新增问题
- 灰度阶段：逐步放量提前暴露问题
- 线上阶段：监控指标、告警，及时止损
- 另外，建设和借助基建、工具 提高发现和定位问题的效率

## 二、核心理论与设计原则

### 2.1 四阶段模型：观测、分析、治理、预防

这是整个体系的主线：

1. **观测**：采集事件、指标、日志、调用栈、Dump、环境画像和用户操作上下文。
2. **分析**：按版本、设备、模块、进程、线程和时间聚合，结合调用栈、ETW Trace、日志和代码定位原因。
3. **治理**：修复代码，优化资源使用，增加超时、取消、重试、降级、隔离和恢复策略。
4. **预防**：静态检查、代码审查、自动化测试、性能基线、灰度发布、告警和版本准入。

### 2.2 可观测性三要素

建议把客户端可观测性拆为：

- **Metrics**：回答“发生了多少、影响了多少用户、趋势如何”；
- **Logs**：回答“关键业务步骤走到了哪里、失败原因是什么”；
- **Traces/Profiles**：回答“时间和资源消耗在哪里、调用链和线程状态是什么”。

三者应使用相同的关联字段，例如 `app_version`、`build_id`、`session_id`、`event_id`、`scene` 和 `device_id_hash`，使单个事件可以从指标下钻到日志和现场。

### 2.3 可靠性工程的几个经典原则

#### 预防优先，但允许失败

不能假设网络、磁盘、驱动、权限、内存和第三方模块永远正常。对预期失败设计明确结果：

- 有界超时；
- 可取消；
- 有限重试和指数退避；
- 幂等操作；
- 降级或跳过非核心功能；
- 用户可理解的错误提示；
- 失败后可恢复或可重启。

#### 故障隔离和最小影响半径

把高风险、可重启、资源消耗大的能力放在独立进程或独立任务边界内。主进程不应因为渲染进程、下载器、解码器或 GPU 进程失败而整体退出。

#### 以用户场景和分位数衡量

平均值容易掩盖长尾。启动、卡顿、渲染等场景应关注 `P50/P75/P95/P99`，并同时看失败率、影响用户数和问题持续时长。

#### 优化必须基于测量

性能问题先建立基线，再采样、定位、修改、复测。没有证据的“优化”可能只是增加复杂度，甚至使问题转移到其他线程或其他设备。

## 三、总体架构

### 3.1 分层架构

| 层级 | 内容 |
| --- | --- |
| 业务场景层 | 启动、登录、打开文件、搜索、编辑、导出、退出 |
| 观测层 | 指标、结构化日志、Trace、心跳、异常事件 |
| 现场层 | 崩溃上下文、调用栈、Dump、卡顿快照、资源快照、埋点上报 |
| 诊断层 | 符号化、聚合、ETW/WPA、日志关联、问题归因 |
| 治理层 | 修复、优化、降级、隔离、重启、回滚、用户提示 |
| 预防层 | 静态扫描、测试、性能基线、灰度、告警、准出 |

### 3.2 事件统一模型

所有稳定性和性能事件至少包含：

```json
{
  "event_type": "crash|jank|oom|startup|operation|resource",
  "event_id": "uuid",
  "app_version": "1.0.0",
  "architecture": "x64",
  "scene": "startup",
  "process_role": "main|renderer|worker|watchdog",
  "session_id": "opaque-id",
  "timestamp": "UTC timestamp",
  "duration_ms": 123,
  "device_profile": {},
  "payload": {}
}
```

> 采集内容应遵循最小化原则：不上传用户文件内容、完整命令行、绝对路径中的用户名、业务密钥和不必要的堆内存；设备标识应哈希或使用不可逆匿名标识。

## 四、稳定性建设

本节只整理 Windows 桌面端相关实践。每个问题按“定义问题 -> 设计指标 -> 捕获现场 -> 归因诊断 -> 治理预防”展开；线上指标负责发现问题，Dump、调用栈、ETW Trace 和 Windows 工具负责解释问题。

Windows 现场的公共字段至少包括：版本和构建号、x64/x86/ARM64、Windows 版本与构建号、进程角色、线程角色、场景、发生阶段、设备画像、时间戳和事件 ID。指标分母必须固定，短生命周期进程必须在退出前补报最终值。

### 4.1 崩溃

#### 定义问题

崩溃是进程异常退出，导致闪退、启动失败或功能中断。必须区分核心进程、可自动重启的非核心进程、退出崩溃、主动退出和更新重启。

#### 设计指标

- 崩溃率：崩溃次数 / 进程启动次数或功能使用次数；
- 崩溃用户率：发生崩溃的设备数 / 活跃设备数；
- 核心进程、非核心进程和所有进程分别统计；
- 启动阶段、核心功能、异常代码、版本和调用栈指纹分别聚合；
- 统计新增问题、版本回归和 Top 问题影响用户数。

退出时崩溃、用户主动退出和更新重启不能混入正常崩溃率。事件维度用于衡量频次，用户维度用于衡量影响范围。

#### 捕获现场

- 使用 Crashpad 或等价崩溃基建生成 Dump，同时尽可能捕获故障线程调用栈。
- Windows 兜底可使用 WER LocalDumps 或 ProcDump。
- 现场至少记录异常代码、异常地址、故障线程、进程角色、模块列表、模块名加 RVA 调用栈、版本、关键日志和资源信息。

- 崩溃回调不做网络请求和复杂业务逻辑；
- 采集失败时依次降级为完整栈、模块加 RVA 栈、PC/异常码/线程 ID 和崩溃元数据。Dump 目录要限制大小、数量和保留时间，PDB 必须与发布的 exe/dll 匹配。

#### 归因诊断

- 用 WinDbg、Visual Studio、CDB 或 minidump_stackwalk 分析 Dump 和调用栈，按以下类别归因：

- 代码缺陷：空指针、越界、竞态、堆损坏、未定义行为；
- 主动断言或主动终止；
- OOM 或单次大内存申请失败；
- 第三方注入、系统模块、驱动和安全软件影响；
- 依赖 DLL、架构、构建产物或符号不匹配。

- 按调用栈上的业务模块、系统模块和第三方模块聚合问题指纹。
- 堆损坏、栈溢出和 Loader Lock 要标记为现场采集可能不完整。

#### 治理预防

- 研发和测试阶段启用编译器警告、静态分析、ASan/UBSan 和适用的 Fuzzing；
- 系统/驱动接口边界使用 SEH 做局部保护；
- 高风险模块隔离、阻止加载或提供降级路径。发布准入要求 Dump 可生成、PDB 可解析、主动退出误报可接受；
- 线上激增时暂停灰度、关闭功能或回滚。

### 4.2 卡顿与卡死

#### 定义问题

卡顿是线程超过场景阈值没有完成预期进度；卡死是卡顿后在观察窗口内没有恢复。UI 线程、Renderer 主线程、渲染线程、IPC 线程和业务主线程应分别观测。Windows UI 场景可参考 5/10 秒卡顿阈值，是否卡死必须由恢复结果判断。

#### 设计指标

- 卡顿率、卡死率；
- 卡顿时长 P50/P95/P99 和卡顿时长占比；
- 卡顿开始、恢复和卡死事件数；
- UI、Renderer、IPC 等线程维度的影响用户数；
- JS Long Task 统计值（若客户端包含 Web 容器）。

用“观测线程检查被观测线程心跳”的方式判断：超过阈值记录卡顿，恢复心跳记录恢复时长，观察窗口内没有恢复才记为卡死。退出阶段卡顿/卡死应单独统计。

#### 捕获现场

- 生产环境优先使用独立 watchdog 进程监控主进程心跳或 IPC。
- 卡顿现场记录最后心跳、线程 ID、线程角色、资源快照、关键日志，并按采样或白名单生成 Dump/调用栈。
- 使用 SuspendThread 有自死锁风险，必须记录采集前后心跳，并保证恢复线程、关闭句柄和超时退出。

#### 归因诊断

- Windows 使用 WPR/WPA 分析调度、CPU、线程状态和调用栈，使用 Procmon 分析文件 IO，使用 ProcDump 捕获未响应现场，使用 WinDbg 分析 Dump。
- 重点区分执行大任务、文件 IO 阻塞、等待同步原语、线程 join、系统调用被拦截、第三方模块耗时和系统资源紧张。

#### 治理预防

- UI 线程不执行不可控大任务、同步文件 IO 和长时间第三方调用；
- 大任务改为可取消异步任务；
- 所有等待有超时；
- 减少锁粒度和持有时间，消除忙轮询；
- 非核心子进程支持自动重启或功能降级。修复必须提供同场景 WPR/WPA 前后对比。



### 4.3 OOM 与内存泄漏

#### 定义问题

OOM 是系统或进程无法满足内存申请，导致功能失败、进程退出或影响其他软件。内存泄漏是操作结束后资源没有释放，使内存持续增长。Windows 上应首先区分系统 Commit 不足、进程占用过大和单次申请过大。

#### 设计指标

- OOM 率、分配失败次数、单次大分配次数；
- 进程 Private Working Set、Private Bytes、Commit、虚拟地址空间；
- 系统 Commit Limit、Committed Bytes、物理内存总量和可用量；
- 进程/子进程内存峰值、P50/P95/P99；
- 缓存、对象、句柄、GDI/User 对象数量；
- 核心操作后和空闲 5/15/30 分钟后的内存水平及增长斜率。

指标关联设备内存容量、系统剩余内存、版本和进程角色。

#### 捕获现场

- OOM 时补报当前申请大小、进程/系统内存总量和余量、Commit Limit、故障线程、调用栈和场景。按启动、核心操作、空闲和退出前采集资源快照。Windows 原生模块使用 VMMap/Process Explorer，系统压力使用 RAMMap；
- Web 容器的 Heap Snapshot 必须脱敏。

#### 归因诊断

- 调用栈和内存信息结合分析：系统虚拟内存不足通常不能靠业务优化解决；
- 进程占用过大要定位缓存、图片、媒体、对象和模块；
- 单次申请过大要检查大数据拷贝、IPC 反序列化膨胀和大文件一次性加载；
- 长期增长要检查异常、重试和取消路径的资源持有。

#### 治理预防

- 设置缓存上限和淘汰策略；
- 大文件流式处理；
- 减少大对象复制；
- 使用 RAII、智能指针和句柄封装；
- 压力下释放非核心资源；
- 非核心路径 OOM 时允许跳过后续逻辑，核心路径提示用户并执行可控恢复。测试阶段用 LSan 或等价工具，重复 N 轮验证 Private Bytes 增长斜率而不是只看单点峰值。



### 4.4 异常、启动失败、白屏和黑屏

#### 定义问题

异常是预期内执行失败；启动失败是进程或核心启动路径未完成；白屏/黑屏是没有异常提示但用户没有获得有效渲染结果。Windows 桌面端应把主进程、Renderer/GPU 进程、依赖 DLL、网络和驱动问题分开统计。

#### 设计指标

- 启动成功率和异常退出率；
- JS 代码异常率、HTTP 请求失败率、Web 容器加载失败率、下载成功率和加载成功率；
- 白屏/黑屏率、持续时长分位数和持续时长占比；
- 按启动、配置、依赖、窗口、渲染和核心数据阶段拆分。

业务建设路径为：业务 -> 核心场景 -> 核心路径 -> 关键节点 -> 潜在异常 -> 观测指标 -> 指标口径 -> 现状水位 -> 优化和防劣化。

#### 捕获现场

- 每个关键节点上报成功/失败、耗时、错误码和阶段 ID。JS 异常记录 uncaughtException、unhandledRejection、调用栈和 source map 版本；
- 白屏/黑屏在页面加载完成及渲染链路上检查可见元素和采样渲染结果。启动和异常事件要考虑崩溃、网络故障时埋点丢失，必要时由独立进程补报。

#### 归因诊断

- 按阶段和错误码归因：依赖 DLL 缺失或 API 版本不兼容、权限/配置失败、网络和代理失败、Renderer/GPU 崩溃、关键资源加载失败、关键进程被安全软件拦截、驱动不兼容或加载耗时过长。
- 白屏/黑屏没有统一根因，应先排除崩溃、卡死、异常和耗时过长。

#### 治理预防

- 打包后扫描 DLL 依赖和代码产物，检查最低支持 Windows 版本；
- 弱网、低磁盘、驱动和安全软件环境纳入测试；
- GPU 失败提供软件渲染或功能降级；
- 核心资源失败展示可操作错误页；
- 线上引导用户升级系统、驱动或安装补丁。



## 五、性能建设

耗时类用分位数，资源类同时记录峰值、分位数和超阈值持续时间；每次优化必须通过固定设备、固定数据、固定缓存状态的前后对比验证。

### 5.1 耗时

#### 定义问题

长耗时场景会增加用户等待；短耗时场景会表现为渲染卡顿和丢帧。Windows 桌面端重点关注冷启动、核心交互、核心接口和单帧渲染。

#### 设计指标

- 耗时分位数；
- 秒开率、X 秒内完成率；
- 冷启动、核心场景加载、核心接口请求耗时；
- 单帧耗时、丢帧/卡顿率统计值。

不要用平均值替代长尾；不同场景分别定义成功完成、可交互和超时。

#### 捕获现场

- 在启动、核心操作和接口请求的阶段边界埋点，记录开始/结束、阶段耗时、数据量、磁盘类型、版本和设备。
- 短生命周期任务在退出前补报。
- 冷启动测试明确是否清理系统文件缓存。

#### 归因诊断

- Windows 使用 WPR 采集 ETW，WPA 按进程、线程、调用栈和 IO 下钻；
- 文件 IO 用 Procmon，Web 容器页面用 DevTools Performance。将阶段日志与 CPU、磁盘、线程调度和网络时间线对齐，区分串行初始化、同步 IPC、文件 IO、网络等待和渲染开销。

#### 治理预防

- 拆分初始化和加载阶段；
- UI 线程不做大任务、同步 IO 或同步网络等待；
- 增加超时和取消；
- 审查文件 IO 和网络请求；
- 以同设备同场景的 P50/P95/P99 作为版本准出和防回归基线。



### 5.2 内存占用

#### 定义问题

进程占用过多内存会导致自身、系统或其他进程内存不足，最终表现为 OOM、卡顿和功能失败。内存占用和内存泄漏必须分开观察。

#### 设计指标

- 进程内存占用分位数和峰值分位数；
- 内存占用长时间超过阈值的异常率；
- 内存泄漏率、泄漏速率（MB/h）和每轮操作增长量；
- Windows Private Working Set（物理内存）和 Private Bytes（虚拟内存）；
- 系统 Commit Limit/Committed Bytes、物理内存总量/余量；
- JS Heap 和业务 Renderer 进程内存。



#### 捕获现场

- 固定在启动后、核心操作后、空闲和退出前采集。Windows 进程分布用 VMMap/Process Explorer，系统物理页分布用 RAMMap；
- Web Heap Snapshot 只在受控环境采集并脱敏。

#### 归因诊断

- 使用 WPR/WPA 分析内存申请/释放时间线，VMMap 分析进程地址空间和堆分布，RAMMap 判断系统压力。Chromium 容器可用 memory-infra 按 Browser/Renderer 等进程拆分；
- 不能把 VirtualAlloc 时间点直接等同于业务对象申请时间。

#### 治理预防

- 设置缓存上限和淘汰；
- 大文件流式处理；
- 减少复制和 IPC 膨胀；
- 非核心资源主动释放；
- 测试阶段用 LSan 做模块级泄漏检查；
- 版本准出同时检查峰值、空闲回落和长时间增长斜率。



### 5.3 CPU 使用率

#### 定义问题

进程 CPU 占用过高会挤占其他进程资源，并造成发热和功耗增加。Windows 采集时必须区分进程 CPU、线程 CPU、系统 CPU 和 Processor Time/Processor Utility 两种口径。

#### 设计指标

- 进程和系统 CPU 使用率分位数；
- CPU 峰值分位数和长时间超过阈值的异常率；
- 业务 Renderer 进程、主线程和关键后台线程分别统计；
- 空闲、核心场景和后台运行状态分别统计。

进程/线程 CPU 需要明确是否按 CPU 核心数归一化，避免把单核百分比误当整机百分比。

#### 捕获现场

- 线上用任务管理器、PerfMon、Process Explorer 或 PDH 定时观测；
- 诊断现场记录采样间隔、进程/线程 ID、线程角色和功耗状态。高 CPU 期间保存 WPR Trace，而不是只上传一个 CPU 数字。

#### 归因诊断

- Windows 使用 WPR/WPA：先按进程和线程定位，再看 CPU Usage Sampled/精确 CPU 调用栈，最后核对 Ready Time、Context Switch、锁等待和系统调用。
- 调用栈聚合前裁剪采集器和通用框架帧，重点保留业务热点。

#### 治理预防

- 大任务拆为可取消后台任务；
- 消除固定周期忙轮询和异步死循环；
- 减少锁粒度和持有时间；
- 控制线程数、任务队列和并发度；
- 优化热点数据分配、拷贝、缓存局部性和算法复杂度。



### 5.4 GPU 使用率

#### 定义问题

GPU 占用过高会影响其他进程渲染，并造成发热和功耗增加。Windows 桌面端要区分显卡、GPU Engine 和进程；Chromium 场景通常只能整体观察，不能直接归因到某个页面。

#### 设计指标

- 独立显卡/集成显卡和实际使用显卡；
- GPU Engine（3D、Copy、Video Decode、Video Encode 等）；
- 进程 GPU、系统 GPU、峰值和超阈值持续时间；
- 帧耗时、丢帧率、显存和纹理规模。



#### 捕获现场

- 使用任务管理器、PerfMon、Process Explorer 和 PDH 观测；
- PDH 可读取 `\\GPU Engine(*)\\Utilization Percentage`。现场同时记录 GPU 型号、驱动版本、Adapter、Engine、分辨率、DPI、刷新率和硬件加速开关。

#### 归因诊断

- Windows 使用 WPR/WPA 和 GPUView 分析 GPU 队列、提交、调度、同步和 Present；
- Web 容器补充 DevTools Performance/Chrome Tracing。不要把总 GPU 百分比直接当作页面或业务根因。

#### 治理预防

- 限制纹理、图片、视频尺寸和生命周期；
- 减少过度绘制、重复上传和同步提交；
- 按设备能力降低渲染质量；
- 针对不同 GPU、驱动、多屏、高 DPI 和软件渲染路径建立回归基线。



### 5.5 文件 IO

#### 定义问题

文件 IO 过多、过大或被安全软件拦截，会在 HDD 上显著增加耗时，并可能阻塞 UI 线程造成卡顿或卡死。

#### 设计指标

- 文件 IO 分位数、峰值分位数和超阈值异常率；
- 次数、大小、读取/写入；
- 进程文件 IO、系统文件 IO 和业务模块；
- UI 线程同步 IO 次数、耗时和被拦截次数。

路径必须脱敏，不能上传账户名和业务文件名。

#### 捕获现场

- 记录操作开始/结束、访问类型、大小、路径类别、缓存状态、线程角色、返回 Result、Duration 和过滤驱动信息。
- 冷启动分别建立系统缓存命中和冷缓存两套基线。

#### 归因诊断

- 使用 Procmon 过滤进程名，查看 IRP 类型、路径、Result、Duration、调用栈和安全软件过滤驱动；
- 使用 WPR/WPA 分析 IO 与线程调度的关联，确认是否阻塞 UI 或启动阶段。

#### 治理预防

- UI 线程禁止不可控同步文件 IO；
- 合并小文件写入；
- 日志滚动并限制总量；
- 临时文件加原子替换；
- 明确 FlushFileBuffers 的必要性；
- 缓存和后台写入设置大小、并发和磁盘配额。



### 5.6 网络 IO

#### 定义问题

网络 IO 问题包括带宽占用过大、请求耗时、下载失败、重试风暴和网络异常阻塞业务。

#### 设计指标

- 网络 IO 分位数、峰值分位数和超阈值异常率；
- 请求次数、上下行大小、进程/系统网络 IO 和业务模块；
- DNS、连接、TLS、首包、下载、解析耗时；
- 网络错误、服务端错误、业务错误和重试次数。

#### 捕获现场

- 记录请求场景、阶段耗时、响应体积、网络类型、代理状态、超时类型、重试次数和最终结果；
- 不记录敏感 URL 参数、请求体和密钥。短生命周期进程退出前补报累计网络量。

#### 归因诊断

- 使用 Procmon、系统网络计数器、DevTools Network 和服务端指标区分离线、DNS、TLS、代理、防火墙、丢包、高延迟、服务端错误、响应体过大和客户端解析慢。
- 弱网测试覆盖慢速、延迟、丢包和断网恢复。

#### 治理预防

- 所有请求设置连接、读取和整体超时；
- 重试只用于可恢复错误并指数退避；
- 业务操作保证幂等；
- 上传/下载设置并发、带宽和磁盘配额；
- 网络失败区分离线、传输层和业务层，不在主线程同步等待。



### 5.7 磁盘占用

#### 定义问题

软件占用过多磁盘空间会导致用户磁盘不足；Windows 系统盘空间不足还可能造成虚拟内存不足并放大 OOM 风险。

#### 设计指标

- 本地缓存占用分位数和超阈值异常率；
- 磁盘空间不足率和文件写入失败率；
- 安装包大小、安装目录大小、更新包大小；
- 日志、图片缓存、媒体缓存、临时文件和功能目录分别统计。



#### 捕获现场

- 记录磁盘类型、总容量、剩余容量、安装盘/缓存盘、目录类别、文件数量和版本增量。
> 目录采集支持按功能开关启用，并限制递归深度和采集目录，避免采集用户文件内容。

#### 归因诊断

- 使用 WinDirStat、PowerShell 和构建产物清单按子目录定位增长，关联版本、功能开关和更新任务；
- 分析写入失败时同时记录错误码和剩余空间。

#### 治理预防

- 缓存、日志和更新包设置上限、滚动和清理策略；
- 低磁盘空间时提示用户，停止非必要写入并保留核心功能；
- 版本准入比较包体和安装目录基线，异常增量必须说明原因；


## 六、诊断工具链

### 6.1 常用工具

| 工具 | 适用问题 |
| --- | --- |
| Process Explorer | 进程、线程、句柄、模块、CPU 和内存细节 |
| WPR | 采集 Windows ETW 性能 Trace |
| WPA | 分析 CPU、调度、IO、内存、启动和图形数据 |
| GPUView | GPU 队列、提交、调度和同步分析 |
| WinDbg | Dump、异常、线程、调用栈和内存分析 
| Crashpad/Breakpad | 崩溃捕获、上报和符号化链路 |

### 6.2 标准诊断流程

1. 明确用户可感知现象和复现步骤；
2. 确认版本、系统、架构、设备、驱动和第三方注入环境；
3. 确认问题是稳定性、性能、资源还是兼容性；
4. 先看大盘趋势和分布，再看单个现场；
5. 对卡顿/耗时问题采集 ETW Trace；
6. 对崩溃/卡死问题解析调用栈或 Dump；
7. 将日志时间线、线程状态、资源曲线和调用栈关联；
8. 形成“证据、假设、验证、修复、回归”的问题记录；
9. 修复后做同场景对比和长时间稳定性验证。

### 6.3 问题归因分类

建议至少分为：

- 代码缺陷：空指针、越界、竞态、死锁、未定义行为、资源泄漏；
- 任务设计：大任务运行在 UI 线程、没有取消、没有超时；
- 资源问题：内存、CPU、GPU、磁盘、网络、句柄不足；
- 环境问题：系统版本、驱动、安全软件、输入法、第三方注入；
- 构建问题：符号缺失、依赖缺失、架构错误、安装包产物变化；
- 数据问题：异常数据量、超大文件、损坏缓存、脏配置；
- 产品策略问题：重试风暴、缓存无界、失败后没有恢复路径。


## 七、开发、测试与发布准入

### 7.1 开发阶段

- 结构化日志和错误码先于功能上线；
- 核心接口明确超时、取消、重试和错误传播策略；
- 资源使用采用 RAII 和所有权约束；
- C++ 启用编译器警告、静态分析、clang-tidy 或等价规则；
- 对跨 DLL、回调、C ABI、Windows API 和线程模型做接口约束；
- 关键路径增加可关闭的性能计时点；
- Code Review 必须检查异常路径和资源释放路径。

### 7.2 测试阶段

测试矩阵至少包含：

| 维度 | 样例 |
| --- | --- |
| 系统 | 最低支持版本、当前主版本、企业环境版本 |
| 架构 | x64、必要时 x86/ARM64 |
| 设备 | 低配、主流、高配；HDD/SSD；不同 GPU |
| 网络 | 正常、弱网、高延迟、丢包、断网恢复 |
| 数据 | 空数据、边界数据、超大文件、损坏缓存 |

> 线上发布版本不能只验证 Debug 或关闭优化的行为。

### 7.3 性能基线

每个核心场景建立基线：

```text
场景 -> 固定设备/数据/环境 -> 重复 N 次 -> 记录 P50/P95/P99
     -> CPU/内存/GPU/网络 -> 和上一版本比较
```

建议将以下指标设置为准出项：

- 版本没有**新增/激增**高严重度**卡顿、卡死和崩溃**问题；（**必须项**）
- 启动耗时不得超过基线允许增量；
- 核心场景内存峰值和空闲回落符合基线；
- CPU 高占用持续时间不超过阈值；
- 包体、安装目录、缓存和日志明显增量有明确原因；



### 7.4 灰度与止损

发布必须支持：

- 按版本、用户群和功能开关灰度；
- 发现指标激增时暂停放量；
- 远程关闭高风险功能；
- 回滚或强制升级；
- 对单个子进程自动重启；

告警条件建议分为：

- **新增**：出现新的问题指纹；
- **激增**：相比基线或环比显著增长；
- **出现即告警**：重点用户、灰度版本、核心功能出现单例也要关注。

## 八、通用方案

稳定性和性能数据必须能够从线上指标下钻到版本、Windows 系统、设备、发生阶段和用户操作，再关联到日志、调用栈、Dump 或 ETW Trace。

### 8.1 通用指标设计

#### 问题发生率

适用于崩溃率、卡顿率、异常率、白屏/黑屏率和秒开率：

```text
PV = 问题发生次数 / 功能使用次数或活跃与启动次数
UV = 受影响设备数或用户数 / 活跃设备数或用户数
```

分母必须使用活跃量或真实功能使用量，不能只使用启动量。PV 衡量问题发生频次，UV 衡量影响范围，两者必须同时保留。

#### 问题持续时长占比

适用于卡顿、卡死、白屏和黑屏：

```text
问题持续时长占比 = 问题持续时长 / 功能使用时长
```

卡顿、恢复和卡死要分别记录开始时间、结束时间和最终状态。退出阶段发生的问题单独统计，不能与正常使用阶段混合。

#### 样本分布

适用于耗时、内存、CPU/GPU 使用率、文件 IO 和网络 IO：

- 开区间长尾指标优先使用 P50/P75/P90/P99，不用平均值掩盖尾部；
- 数值范围可控时可同时报告均值和分位数；
- 统计前排除负数、极大值、重复上报、采集失败和无观测意义的样本；
- 样本量过大时先按版本、设备和场景分层采样，再计算分布。

#### 定时采样

- 内存、句柄、GDI/User 对象属于单点指标，初始化完成后采集并按固定间隔补采；
- CPU/GPU、网络和文件 IO 属于区间差值，使用两次采样差值除以采样间隔；
- CPU 采集明确进程/线程口径、CPU 核心数归一化和 Processor Time/Processor Utility 口径；
- 非常驻的进程、线程或 Renderer 必须在启动后记录一次、退出前再记录一次，避免漏采；
- 每个采样值携带版本、场景、进程角色、线程角色和设备画像。

### 8.2 通用归因方案

#### 按时间看趋势

按年、季度、月、周、日、小时、分钟和秒观察问题变化，并与程序版本、灰度批次和发布节点对齐。Windows 桌面端至少要能回答：

- 问题是否从某个版本开始；
- 是否集中在启动、退出、某个核心操作或运行一段时间后；
- 是否与 uptime、系统更新、驱动更新或功能开关变化相关；
- 问题是持续增长、偶发尖峰还是只存在于灰度人群。

#### 按维度看分布

按以下维度切分崩溃、卡顿、异常和性能数据：

- 程序版本、构建号和功能开关；
- Windows 版本、系统构建号和架构；
- CPU、内存、GPU、驱动、磁盘类型和屏幕 DPI；
- 进程角色、线程角色和发生阶段；
- 用户操作、核心场景和数据规模；
- 网络类型、延迟、丢包、代理和安全软件环境。

稳定性问题先看大盘趋势和分布，再下钻单个现场。不能只根据一份 Dump 或一次 Trace 推断整体问题。

#### 证据关联

统一使用事件 ID、会话 ID、版本、构建号、进程 ID、线程 ID、场景和时间戳关联：

```text
线上指标
  -> 问题指纹/分布
  -> 版本、设备、阶段和操作
  -> 日志时间线
  -> 调用栈、Dump 或 WPR Trace
  -> 假设、验证、修复和回归
```

### 8.3 通用监控方案

#### 判断条件

- **新增**：出现一类新的崩溃、卡顿、异常或性能问题；
- **激增**：存量问题次数或指标相对基线、同比或环比显著增长；
- **出现**：重点用户、内部用户、灰度版本或核心功能出现一例即告警。

#### 样本范围

- 大盘整体；
- 正式版本、灰度版本和测试版本；
- 重点用户、内部用户和受影响设备；
- Windows 系统版本、架构、驱动和设备画像；
- 核心启动、核心交互、文件、网络和渲染场景。

#### 时间范围和执行方式

- 天级：版本趋势、用户影响范围和长期资源增长；
- 小时级：灰度放量、版本发布和问题激增；
- 分钟级：核心功能、重点用户和线上事故。

执行方式包括自动告警、定时巡检和定时推送。告警必须包含问题指纹、版本、Windows 环境、影响用户数、样本量、基线对比和最近现场链接，避免只发送一个比例数字。

### 8.4 通用止损方案

止损动作必须在发布前验证，且能够通过 Windows 客户端或云控执行：

- **功能开关**：关闭高风险模块，切换软件渲染、低成本路径或兼容实现；
- **回滚版本**：支持回滚、强制升级和静默升级；
- **自动恢复**：重启可隔离的 GPU、Renderer、下载器或其他子进程；
- **配置修复**：下发任务清理损坏缓存、修复配置或修改本地文件；
- **资源止损**：停止非必要后台任务、缓存写入和高成本重试；
- **公告和提示**：对不可恢复场景提示用户，保留现场并引导升级；
- **客服联动**：将版本、设备画像、日志、Dump/Trace 和问题指纹组成标准诊断包。

执行云控修改本地文件时必须有版本校验、备份、幂等和回滚机制，不能把止损任务变成新的数据损坏来源。

### 8.5 Windows 设备画像

#### 内存

- 总容量、可用容量；
- 内存通道数、DDR 类型和频率；
- 进程 Private Working Set、Private Bytes、Commit；
- 系统 Commit Limit、Committed Bytes、物理内存总量和余量。

#### CPU

- 型号、主频、核心数、线程数；
- 处理器架构和性能分级；
- 进程/线程 CPU 口径及是否按核心数归一化。

#### GPU

- 所有 GPU、实际使用 GPU；
- 独立显卡/集成显卡；
- GPU 型号、驱动版本和 GPU Adapter；
- 主要 GPU Engine 使用情况。

#### 磁盘

- HDD/SSD/NVMe 类型；
- 总容量和剩余容量；
- 安装盘、缓存盘和数据盘；
- 日志、缓存、更新包所在目录及目录大小。

#### 屏幕

- 屏幕数量；
- 分辨率；
- DPI；
- 刷新率。

设备画像必须与问题事件关联，并对账户名、绝对路径、用户文件名和设备标识脱敏。

## 九 如何提高代码质量

- 防御性编程：参数校验、边界检查、错误码和资源所有权明确；
- C/C++ 使用编译器警告、静态分析、clang-tidy、ASan/UBSan 和适用的 Fuzzing；
- 对跨 DLL、C ABI、Windows API、回调和线程模型建立接口约束；
- Code Review 必须检查异常路径、取消路径、超时路径和资源释放路径；
- 关键路径增加结构化日志和错误码；
- 将重复出现的线上问题沉淀为规则、测试用例、代码扫描项或发布准入项；
- 定期更新规范、扫描规则和问题案例，避免同类 Windows 兼容性问题反复出现。

## 十、运行环境与技术支持

### 10.1 环境复杂性

线上问题不能只按业务代码归因，还要记录运行环境造成的影响：

- 第三方注入：输入法、安全软件、录屏工具和驱动模块可能导致崩溃或卡死；
- 系统差异：Windows 版本、系统文件、权限、防火墙和默认浏览器可能导致启动失败或兼容性问题；
- 资源竞争：浏览器标签页、大型游戏和其他高负载程序会放大 CPU、内存和 GPU 问题；
- 硬件差异：低配设备、HDD、显卡驱动和硬件缺陷会改变同一版本的表现。

设备画像至少包括 Windows 版本和构建号、架构、CPU、内存容量与剩余量、GPU 与驱动、磁盘类型与剩余空间、屏幕数量、分辨率、DPI 和刷新率。采集绝对路径、账户名和用户文件信息时要做脱敏。

### 10.2 客服与技术支持

将高频问题沉淀为标准诊断流程和用户话术：

1. 客服先收集版本、复现步骤、设备画像和问题发生时间；
2. 客户端自动采集结构化日志、事件时间线、资源快照和必要的 Trace；
3. 工具根据规则给出网络、驱动、第三方注入、磁盘空间或版本问题的初步结论；
4. 无法自动归因时再升级给研发，并附带完整诊断包和问题指纹。

对可检测的问题，应优先转化为产品内检测和提示；对用户环境导致的问题，应沉淀标准话术；对第三方问题，应建立与安全软件、输入法、显卡和操作系统厂商的沟通渠道。
