> 本方案面向 Windows 桌面端软件，覆盖 C/C++ 原生程序、Electron/WebView 容器、混合架构以及多进程客户端。
> 目标是把“出了问题再排查”建设为一套可持续运行的工程系统：问题可观测、现场可捕获、原因可定位、风险可止损、版本可验证。

## 一、目标与适用范围

### 1.1 建设目标

稳定性建设关注“软件是否持续正确地工作”，性能建设关注“软件在可接受资源成本内完成工作”。两者不能割裂：

- 卡顿可能最终表现为崩溃、超时或用户强制退出；
- 内存、CPU、文件 IO 和网络 IO 的失控会放大稳定性风险；
- 没有现场数据的稳定性指标只能告诉我们“发生了什么”，不能回答“为什么发生”；
- 没有版本基线的性能数据无法判断优化是否有效，也无法阻止回归。

建设目标应落到以下闭环：

```text
定义用户场景
  -> 建立指标和基线
  -> 采集事件与现场
  -> 聚合、归因、定位
  -> 修复、优化、降级或回滚
  -> 版本准出和持续回归
```

### 1.2 关注对象

| 类别 | 典型问题 | 主要结果 |
| --- | --- | --- |
| 稳定性 | 崩溃、OOM、卡顿/卡死、白屏、黑屏、启动失败、异常退出 | 用户无法继续使用或数据丢失 |
| 性能 | 启动慢、CPU 高、内存增长、GPU 高、IO 阻塞、网络慢 | 用户感知变差、设备资源被挤占 |
| 工程能力 | 日志缺失、符号不匹配、无法复现、告警失效、无法回滚 | 定位和恢复成本过高 |
| 运行环境 | Windows 版本、驱动、安全软件、输入法、第三方注入、硬件差异 | 同一版本在不同设备表现不同 |

### 1.3 保障环节

● 开发阶段：从源头上避免出现问题，对于预期内的问题设计应对策略（降级 fallback、自动恢复/主动重启、重试失败提示）
● 测试阶段：通过测试拦截新增问题
● 灰度阶段：逐步放量提前暴露问题
● 线上阶段：监控指标、告警，及时止损
● 另外，建设和借助基建、工具 提高发现和定位问题的效率

## 二、核心理论与设计原则

### 2.1 四阶段模型：观测、分析、治理、预防

这是整个体系的主线：

1. **观测**：采集事件、指标、日志、调用栈、Dump、环境画像和用户操作上下文。
2. **分析**：按版本、设备、模块、进程、线程和时间聚合，结合调用栈、ETW Trace、日志和代码定位原因。
3. **治理**：修复代码，优化资源使用，增加超时、取消、重试、降级、隔离和恢复策略。
4. **预防**：静态检查、代码审查、自动化测试、性能基线、灰度发布、告警和版本准入。

### 2.2 可观测性三要素

建议把客户端可观测性拆为：

- **Metrics**：回答“发生了多少、影响了多少用户、趋势如何”；
- **Logs**：回答“关键业务步骤走到了哪里、失败原因是什么”；
- **Traces/Profiles**：回答“时间和资源消耗在哪里、调用链和线程状态是什么”。

三者应使用相同的关联字段，例如 `app_version`、`build_id`、`session_id`、`event_id`、`scene` 和 `device_id_hash`，使单个事件可以从指标下钻到日志和现场。

### 2.3 可靠性工程的几个经典原则

#### 预防优先，但允许失败

不能假设网络、磁盘、驱动、权限、内存和第三方模块永远正常。对预期失败设计明确结果：

- 有界超时；
- 可取消；
- 有限重试和指数退避；
- 幂等操作；
- 降级或跳过非核心功能；
- 用户可理解的错误提示；
- 失败后可恢复或可重启。

#### 故障隔离和最小影响半径

把高风险、可重启、资源消耗大的能力放在独立进程或独立任务边界内。主进程不应因为渲染进程、下载器、解码器或 GPU 进程失败而整体退出。

#### 以用户场景和分位数衡量

平均值容易掩盖长尾。启动、卡顿、渲染等场景应关注 `P50/P75/P95/P99`，并同时看失败率、影响用户数和问题持续时长。

#### 优化必须基于测量

性能问题先建立基线，再采样、定位、修改、复测。没有证据的“优化”可能只是增加复杂度，甚至使问题转移到其他线程或其他设备。

## 三、总体架构

### 3.1 分层架构

```text
┌──────────────────────────────────────────────────────────┐
│ 业务场景层：启动、登录、打开文件、搜索、编辑、导出、退出 │
├──────────────────────────────────────────────────────────┤
│ 观测层：指标、结构化日志、Trace、心跳、异常事件          │
├──────────────────────────────────────────────────────────┤
│ 现场层：崩溃上下文、调用栈、Dump、卡顿快照、资源快照、埋点上报       │
├──────────────────────────────────────────────────────────┤
│ 诊断层：符号化、聚合、ETW/WPA、日志关联、问题归因          │
├──────────────────────────────────────────────────────────┤
│ 治理层：修复、优化、降级、隔离、重启、回滚、用户提示        │
├──────────────────────────────────────────────────────────┤
│ 预防层：静态扫描、测试、性能基线、灰度、告警、准出          │
└──────────────────────────────────────────────────────────┘
```

### 3.2 事件统一模型

所有稳定性和性能事件至少包含：

```json
{
  "event_type": "crash|jank|oom|startup|operation|resource",
  "event_id": "uuid",
  "app_version": "1.0.0",
  "architecture": "x64",
  "scene": "startup",
  "process_role": "main|renderer|worker|watchdog",
  "session_id": "opaque-id",
  "timestamp": "UTC timestamp",
  "duration_ms": 123,
  "device_profile": {},
  "payload": {}
}
```

> 采集内容应遵循最小化原则：不上传用户文件内容、完整命令行、绝对路径中的用户名、业务密钥和不必要的堆内存；设备标识应哈希或使用不可逆匿名标识。

## 四、稳定性建设

每个稳定性主题都按“定义问题 -> 设计指标 -> 捕获现场 -> 归因诊断 -> 治理预防”展开。指标必须绑定用户场景、进程或线程、版本和设备画像，并明确分母、采样窗口、数据脱敏和采集失败时的降级路径。

### 4.1 崩溃

#### 定义问题

崩溃是进程因未处理异常或主动终止而异常退出，表现为闪退、启动失败、功能中断或数据未保存。应区分主进程、可自动重启的子进程、退出时崩溃和更新重启。

#### 设计指标

- 崩溃事件率：崩溃次数 / 进程启动次数或功能使用次数；
- 崩溃用户率：发生崩溃的设备数 / 活跃设备数；
- 主进程、Renderer、GPU 和其他子进程分别统计；
- 启动阶段、核心功能和 Top 问题影响用户数分别统计。

同时保留事件维度和用户维度，固定分母并写入指标口径。

#### 捕获现场

组合方案：[**本地调用栈捕获** + **Dump 捕获**](https://fzhenkun.github.io/posts/windows-crash-stack-symbolization-without-dump/)记录并上传故障线程、线程角色、模块身份、模块名加 RVA 调用栈、版本、关键日志和 MiniDump。

#### 归因诊断

按调用栈、异常代码和模块归因：代码缺陷、主动断言、OOM/大内存申请失败、第三方注入/驱动/安全软件影响，以及构建产物、依赖、符号或架构不匹配。Windows 可使用 Crashpad/Breakpad 捕获，使用 Visual Studio、WinDbg 或 minidump_stackwalk诊断。堆损坏、栈溢出和 Loader Lock 要保留采集可能失败的结论。

#### 治理预防

研发和测试阶段启用编译器警告、静态分析等适用检测；对系统、驱动和第三方模块边界使用 SEH；高风险模块隔离或降级；区分主动退出、用户退出、更新重启和真正崩溃；线上激增时暂停放量或关闭功能。



### 4.2 卡顿与卡死

#### 定义问题

卡顿是被观测线程超过场景阈值没有完成预期进度；卡死是卡顿后在观察窗口内没有恢复。一次超时不能直接判定为卡死，比如一次卡顿超时持续 30s 仍未恢复可判定未卡死。应分别观测 UI、Renderer、IPC和业务主线程。

#### 设计指标

- 场景化卡顿率（一般 5/10 s）和卡死率 (一般 30 s)；
- 平均值容易掩盖长尾问题，关注 P50/P95/P99；
- UI、Renderer、IPC 等线程维度的影响用户数。

watchdog 心跳超时记录卡顿开始，恢复记录恢复时长，持续无心跳记录卡死。

#### 捕获现场

优先由独立 watchdog 进程监控主进程心跳或 IPC，卡顿时采集线程状态、日志、资源快照、调用栈或 Dump。SuspendThread 可能因目标线程持有堆锁、Loader Lock 或业务锁造成自死锁，必须保证恢复线程、关闭句柄和超时退出。

#### 归因诊断

结合调用栈、 Dump和 日志区分 UI 大任务、文件 IO/网络/系统调用阻塞、锁竞争/死锁、Renderer 长任务、布局绘制、任务队列堆积及资源紧张。使用 WPR/WPA、WinDbg、DevTools Performance 或 Chrome Tracing。

#### 治理预防

UI 线程只执行轻量工作；大任务拆为可取消后台任务并设置超时；消除忙轮询，缩短锁持有时间，不在锁内做 IO 或第三方调用；子进程支持自动重启和降级。



### 4.3 OOM 与内存泄漏

#### 定义问题

OOM 是系统或进程无法满足内存申请，导致功能失败、进程退出甚至影响其他软件；内存泄漏是操作或场景结束后资源未释放，导致内存持续增长。

#### 设计指标

- 工作集、Private Bytes、Commit、Working Set、虚拟地址空间和 JS Heap；
- 进程/子进程内存分位数与峰值；
- OOM 率、分配失败次数、单次大分配次数；
- 缓存、对象、句柄、GDI/User 对象数量；
- 启动后、核心操作后、空闲 5/15/30 分钟水平和增长斜率。

指标关联设备内存容量、系统剩余内存、版本和进程角色。

#### 捕获现场

OOM 事件记录当前申请大小、进程/系统内存总量与余量、提交限制、故障线程和场景；按生命周期采集快照，必要时使用脱敏 Heap Snapshot；短生命周期进程退出前补采最终值。

#### 归因诊断

区分系统虚拟内存不足、单次申请过大、数据复制或 IPC 膨胀、缓存无界、重试重复持有资源、所有权错误、句柄泄漏和 Web 对象未释放。使用 Process Explorer、VMMap、RAMMap、WPR/WPA、memory-infra、Heap Snapshot 或 MemLab。

#### 治理预防

设置缓存上限和淘汰策略；大文件流式处理；使用 RAII、智能指针和句柄封装；压力下释放非核心资源；检查异常、重试、取消和重启路径；非核心路径 OOM 时跳过后续逻辑，核心路径执行可控恢复。



### 4.4 异常、启动失败、白屏和黑屏(部分问题未实践，纸上谈兵~)

#### 定义问题

异常是预期内执行失败；启动失败是核心启动阶段未完成；白屏或黑屏是窗口存在但用户没有获得有效渲染结果。必须区分主进程异常、Renderer 崩溃、页面 JS 异常、网络失败和 GPU 失败。

#### 设计指标

把进程创建、配置加载、依赖检查、窗口创建、Renderer 启动、首屏可见、首次可交互和核心数据完成拆成阶段，分别记录成功率、失败率、耗时和错误码。重点关注启动成功率、Renderer 崩溃率、页面 JS 异常率、首屏成功率、首次可交互成功率、白屏/黑屏率及持续时长占比。

#### 捕获现场

记录阶段 ID、错误码、版本、source map 版本、网络阶段耗时、GPU 状态和最后一条结构化日志；WebView/Electron 上报 uncaughtException、unhandledRejection 和 Renderer 退出原因；白屏/黑屏结合页面状态、可见元素和采样渲染结果判断。

#### 归因诊断

按阶段定位配置/依赖/权限失败、主进程/Renderer/GPU 崩溃、关键 JS 异常、资源加载失败、网络超时、渲染提交失败、驱动不兼容和第三方拦截。

#### 治理预防

每个阶段提供超时、错误码、降级和恢复路径；GPU 失败时提供软件渲染；核心资源失败时显示可操作错误页；JS 异常、网络失败和 Renderer 崩溃分别处理；测试覆盖冷/热启动、弱网、GPU 兼容性、升级回滚、多屏和高 DPI。



## 五、性能建设(部分问题未实践，纸上谈兵~)

性能指标统一绑定用户场景、设备和数据集。耗时关注分位数和完成率，资源关注峰值、分位数；所有优化必须经过同设备、同数据、同场景复测。

### 5.1 场景耗时与渲染流畅度

#### 定义问题

耗时是用户操作从开始到完成或可继续交互的时间；短耗时场景的风险主要表现为掉帧和交互不连续。

#### 设计指标

- 冷/热启动、首窗、首屏、首次可交互 P50/P95/P99；
- 点击反馈、输入、菜单、搜索、切换、打开/保存/导入/导出耗时；
- 接口 DNS、连接、TLS、首包、下载、解析和渲染分段耗时；
- 秒开率、X 秒内完成率、帧耗时、丢帧率和 JS Long Task 统计值。

#### 捕获现场

在核心路径记录开始、结束和阶段计时，关联版本、场景、数据大小、设备、磁盘、网络和功能开关；短生命周期任务结束时补报最终值。

#### 归因诊断

用 WPR/WPA、DevTools Performance 或框架 Trace 对齐日志，区分初始化串行化、UI 阻塞、同步 IPC、文件 IO、网络等待、布局绘制、过度渲染和驱动问题。长耗时和掉帧分别诊断。

#### 治理预防

关键路径拆阶段并设置预算；UI 工作异步化、可取消且有超时；减少同步 IPC、串行初始化和重复渲染；用 P95/P99 做准出；固定设备、数据和缓存状态重复 N 次。



### 5.2 内存占用

#### 定义问题

内存占用过高或持续增长会导致自己、系统和其他进程内存资源不足，表现为 OOM、卡顿或功能失败。

#### 设计指标

- 进程和系统 内存占用 P50/P95/P99；
- 主线程、Renderer、渲染线程和后台线程 CPU；
- 进程内存：Windows 包括 private working set（物理内存）、private bytes（虚拟内存）
- 系统内存总量、余量：Windows包括 commit charge limit/total（虚拟内存）、physical memory（物理内存）
- JS Heap 占用、业务 Renderer 进程内存占用

#### 捕获现场

采集启动、核心操作、空闲和退出前快照；疑难 Web 问题使用脱敏 Heap Snapshot，不上传用户文件、业务密钥和不必要堆数据。

#### 归因诊断

用 Process Explorer、VMMap、RAMMap、WPR/WPA、memory-infra、Heap Snapshot 或 MemLab 按模块和资源类型定位。

#### 治理预防

缓存设上限；大对象流式处理并减少复制；释放非核心资源；限制图片/媒体/Web 内容生命周期；测试阶段使用 LSan 或等价工具。



### 5.3 CPU 使用率

#### 定义问题

CPU 使用率过高会挤占其他进程资源，导致发热、功耗增加、风扇噪声和交互卡顿。必须区分进程、线程、Renderer 和系统 CPU。

#### 设计指标

- 进程和系统 CPU P50/P95/P99；
- 峰值分位数和持续超阈值比例；
- 主线程、Renderer、渲染线程和后台线程 CPU；
- 空闲、核心场景和后台状态分别统计。

明确 Processor Time 与 Processor Utility 的口径及是否按核心数归一化。

#### 捕获现场

记录采样间隔、进程/线程 ID、线程角色、CPU 核心数、场景和功耗状态；短生命周期任务启动和退出时补采区间值。

#### 归因诊断

用 WPR/WPA 按线程和调用栈下钻，区分计算热点、死循环/忙轮询、上下文切换、锁竞争、系统调用和第三方调用；聚合前裁剪采集器自身帧。

#### 治理预防

大计算拆为可取消后台任务；消除忙轮询；缩短锁持有时间；控制线程数、队列长度和并发度；优化热点数据分配、拷贝、缓存局部性和算法复杂度。



### 5.4 GPU 使用率与渲染资源

#### 定义问题

进程 GPU 使用率过高、显存或纹理资源失控会导致掉帧、发热、功耗增加、驱动超时和其他进程渲染受影响。

#### 设计指标

按独立/集成 GPU、GPU 引擎和进程记录使用率、峰值、持续超阈值比例、帧耗时、丢帧率、显存和纹理规模；Chromium 场景说明通常只能定位整体进程。

#### 捕获现场

记录 GPU 型号、驱动、实际使用 GPU、引擎、分辨率、刷新率和图形开关；Windows 可用 PDH 采集 GPU Engine 利用率。

#### 归因诊断

使用 WPR/WPA、GPUView、框架 Trace、DevTools Performance 或 Chrome Tracing，区分过度绘制、大纹理、频繁上传、队列阻塞、同步等待和驱动问题。

#### 治理预防

限制纹理/媒体尺寸，设置缓存与生命周期，减少重复绘制和同步提交，按设备能力降级；发布前覆盖不同 GPU、驱动、多屏、高 DPI 和软件渲染。



### 5.5 文件 IO

#### 定义问题

文件 IO 过多、过大或被安全软件拦截，会增加启动和业务耗时，并可能阻塞 UI 线程造成卡顿或卡死。HDD、同步目录和低磁盘空间环境风险更高。

#### 设计指标

记录 IO 分位数、峰值分位数、超阈值异常率、次数和大小，并按读取/写入、进程/系统、业务模块、路径类别和缓存命中拆分；路径必须脱敏。

#### 捕获现场

记录操作开始结束、访问类型、大小、路径类别、缓存状态、线程角色和拦截状态；冷启动测试明确文件缓存状态。

#### 归因诊断

使用 Procmon、WPR/WPA 或 File Activity 分析路径、访问类型、耗时、同步等待、重复读写、HDD/SSD 差异和安全软件拦截，并关联 UI 卡顿。

#### 治理预防

UI 线程禁止不可控同步 IO；合并小文件写入；设置日志滚动和总量上限；临时文件加原子替换；谨慎使用 FlushFileBuffers；缓存和后台写入设置配额。



### 5.6 网络 IO

#### 定义问题

网络 IO 的性能问题包括请求耗时、带宽占用、重试风暴、下载失败和网络异常导致的功能阻塞。

#### 设计指标

按请求次数、上下行大小、吞吐分位数、峰值、超阈值时长和失败率统计，并按 DNS、连接、TLS、首包、下载、解析、网络/服务端/业务错误拆分。

#### 捕获现场

每次请求关联场景、接口类别、阶段耗时、响应体积、网络类型、代理状态、重试次数和结果；不记录敏感参数、请求体和业务密钥。

#### 归因诊断

使用日志时间线、系统网络监控、Procmon、DevTools Network 和服务端指标区分离线、DNS、TLS、代理、防火墙、丢包、高延迟、服务端错误、响应体过大和客户端解析慢。

#### 治理预防

所有请求设置连接、读取和整体超时；重试仅用于可恢复错误并指数退避；业务操作保证幂等；上传下载设置并发、带宽和磁盘配额；主线程不等待网络。



### 5.7 磁盘占用

#### 定义问题

安装包、安装目录、更新包、日志和缓存持续增长会耗尽用户磁盘空间；Windows 系统盘空间不足还可能放大虚拟内存和 OOM 风险。

#### 设计指标

- 安装包、安装目录、更新包、日志和缓存大小基线；
- 本地缓存 P50/P95/P99 和超阈值异常率；
- 磁盘空间不足率、文件写入失败率；
- 按功能子目录和版本统计增量。

#### 捕获现场

记录磁盘类型、总/剩余容量、安装盘/缓存盘、目录类别、文件数量和版本增量，排除用户文件内容和敏感路径。

#### 归因诊断

按日志、图片、媒体、更新包、临时文件和缓存目录拆分，使用 WinDirStat、PowerShell 或构建产物清单定位增长，并关联版本和功能开关。

#### 治理预防

为缓存、日志和更新包设置上限、滚动和清理；低磁盘空间时提示并停止非必要写入；版本准入比较包体和安装目录基线，异常增量必须说明原因。



## 六、诊断工具链

### 7.1 常用工具

| 工具 | 适用问题 |
| --- | --- |
| Process Explorer | 进程、线程、句柄、模块、CPU 和内存细节 |
| WPR | 采集 Windows ETW 性能 Trace |
| WPA | 分析 CPU、调度、IO、内存、启动和图形数据 |
| GPUView | GPU 队列、提交、调度和同步分析 |
| WinDbg/CDB | Dump、异常、线程、调用栈和内存分析 
| Crashpad/Breakpad | 崩溃捕获、上报和符号化链路 |

### 7.2 标准诊断流程

1. 明确用户可感知现象和复现步骤；
2. 确认版本、系统、架构、设备、驱动和第三方注入环境；
3. 确认问题是稳定性、性能、资源还是兼容性；
4. 先看大盘趋势和分布，再看单个现场；
5. 对卡顿/耗时问题采集 ETW Trace；
6. 对崩溃/卡死问题解析调用栈或 Dump；
7. 将日志时间线、线程状态、资源曲线和调用栈关联；
8. 形成“证据、假设、验证、修复、回归”的问题记录；
9. 修复后做同场景对比和长时间稳定性验证。

### 7.3 问题归因分类

建议至少分为：

- 代码缺陷：空指针、越界、竞态、死锁、未定义行为、资源泄漏；
- 任务设计：大任务运行在 UI 线程、没有取消、没有超时；
- 资源问题：内存、CPU、GPU、磁盘、网络、句柄不足；
- 环境问题：系统版本、驱动、安全软件、输入法、第三方注入；
- 构建问题：符号缺失、依赖缺失、架构错误、安装包产物变化；
- 数据问题：异常数据量、超大文件、损坏缓存、脏配置；
- 产品策略问题：重试风暴、缓存无界、失败后没有恢复路径。

## 七、开发、测试与发布准入

### 8.1 开发阶段

- 结构化日志和错误码先于功能上线；
- 核心接口明确超时、取消、重试和错误传播策略；
- 资源使用采用 RAII 和所有权约束；
- C++ 启用编译器警告、静态分析、clang-tidy 或等价规则；
- 对跨 DLL、回调、C ABI、Windows API 和线程模型做接口约束；
- 关键路径增加可关闭的性能计时点；
- Code Review 必须检查异常路径和资源释放路径。

### 8.2 测试阶段

测试矩阵至少包含：

| 维度 | 样例 |
| --- | --- |
| 系统 | 最低支持版本、当前主版本、企业环境版本 |
| 架构 | x64、必要时 x86/ARM64 |
| 设备 | 低配、主流、高配；HDD/SSD；不同 GPU |
| 网络 | 正常、弱网、高延迟、丢包、断网恢复 |
| 数据 | 空数据、边界数据、超大文件、损坏缓存 |
| 环境 | 安全软件、输入法、多屏、高 DPI、代理、第三方注入 |
| 生命周期 | 冷启动、热启动、睡眠唤醒、锁屏解锁、升级回滚 |

稳定性测试包括长稳、重复操作、随机操作、故障注入、进程重启、网络切换和磁盘空间压力。C++ 项目应结合 ASan/UBSan 等适用的检测配置；线上发布版本不能只验证 Debug 或关闭优化的行为。

### 8.3 性能基线

每个核心场景建立基线：

```text
场景 -> 固定设备/数据/环境 -> 重复 N 次 -> 记录 P50/P95/P99
     -> CPU/内存/IO/GPU/网络 -> 和上一版本比较
```

建议将以下指标设置为准出项：

- 启动和核心交互耗时不得超过基线允许增量；
- 核心场景内存峰值和空闲回落符合基线；
- CPU 高占用持续时间不超过阈值；
- 包体、安装目录、缓存和日志增量有明确原因；
- 版本没有新增高严重度崩溃和卡死问题；
- 符号、日志、Dump 和回滚链路经过演练。

### 8.4 灰度与止损

发布必须支持：

- 按版本、用户群、设备、系统和功能开关灰度；
- 发现指标激增时暂停放量；
- 远程关闭高风险功能；
- 回滚或强制升级；
- 对单个子进程自动重启；
- 对不可恢复场景提示用户并保留现场；
- 形成客服和技术支持的标准诊断包。

告警条件建议分为：

- **新增**：出现新的问题指纹；
- **激增**：相比基线或环比显著增长；
- **出现即告警**：重点用户、灰度版本、核心功能出现单例也要关注。

## 八、指标口径与监控设计

### 9.1 通用公式

```text
PV = 问题发生次数 / 功能使用次数
UV = 受影响设备数或用户数 / 活跃设备数或用户数
持续时长占比 = 问题持续时长 / 功能使用时长
错误率 = 失败次数 / 尝试次数
```

对开区间长尾使用分位数；统计前排除负数、极大值、重复上报和不具备观测意义的样本。短生命周期进程要在退出前补采最终值，否则采样窗口会产生偏差。

### 9.2 设备画像

设备画像至少包括：

- Windows 版本和构建号；
- x64/x86/ARM64；
- CPU 型号、核心/线程；
- 内存容量和系统剩余内存；
- GPU 型号、驱动版本、实际使用 GPU；
- 磁盘类型、安装盘和缓存盘剩余空间；
- 屏幕数量、分辨率、DPI 和刷新率；

### 9.3 监控与告警

监控至少覆盖以下范围：

- **大盘**：整体趋势、版本趋势和主要问题指纹；
- **版本**：灰度版本、测试版本和正式版本分别观察；
- **人群**：重点用户、内部用户、受影响设备和重点场景；
- **环境**：Windows 版本、驱动、设备画像和网络状态。

告警条件分为三类：

- **新增**：出现新的崩溃、卡死或严重性能问题指纹；
- **激增**：指标相对基线、同比或环比显著增长；
- **出现即告警**：重点用户、灰度版本或核心功能出现单例也需要处理。

短生命周期进程必须在退出前补采最终值；否则 CPU、网络、内存等区间指标容易因为错过采集窗口而产生偏差。统计前还要排除负数、极大值、重复上报和没有观测意义的样本。

### 9.4 止损动作

止损动作应在发布前演练，并与告警条件一一对应：

- 通过功能开关关闭高风险功能或切换到低成本实现；
- 暂停灰度放量，回滚版本或强制升级；
- 重启可隔离的子进程，保留主进程和用户现场；
- 停止非必要缓存写入、后台任务和高成本重试；

## 九、运行环境与技术支持

### 10.1 环境复杂性

线上问题不能只按业务代码归因，还要记录运行环境造成的影响：

- 第三方注入：输入法、安全软件、录屏工具和驱动模块可能导致崩溃或卡死；
- 系统差异：Windows 版本、系统文件、权限、防火墙和默认浏览器可能导致启动失败或兼容性问题；
- 资源竞争：浏览器标签页、大型游戏和其他高负载程序会放大 CPU、内存和 GPU 问题；
- 硬件差异：低配设备、HDD、显卡驱动和硬件缺陷会改变同一版本的表现。

设备画像至少包括 Windows 版本和构建号、架构、CPU、内存容量与剩余量、GPU 与驱动、磁盘类型与剩余空间、屏幕数量、分辨率、DPI 和刷新率。采集绝对路径、账户名和用户文件信息时要做脱敏。

### 10.2 客服与技术支持

将高频问题沉淀为标准诊断流程和用户话术：

1. 客服先收集版本、复现步骤、设备画像和问题发生时间；
2. 客户端自动采集结构化日志、事件时间线、资源快照和必要的 Trace；
3. 工具根据规则给出网络、驱动、第三方注入、磁盘空间或版本问题的初步结论；
4. 无法自动归因时再升级给研发，并附带完整诊断包和问题指纹。

对可检测的问题，应优先转化为产品内检测和提示；对用户环境导致的问题，应沉淀标准话术；对第三方问题，应建立与安全软件、输入法、显卡和操作系统厂商的沟通渠道。
